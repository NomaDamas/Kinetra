# 웹 클라이언트 스케일과 공유 링크 (A0-02)

측정만 한다. 최적화하지 않았다. `spikes/mujoco-limits/REPORT.md`, `spikes/mujoco-wasm/REPORT.md`와 같은 규칙(시드 고정, 부하 기록, 값마다 명령과 머신)을 따른다. 이 파일은 A0-02의 하위 이슈가 각자 자기 절만 채운다.

## A0-02a. 렌더와 실행 스트림 스케일 (이슈 #47)

### 결론 먼저

- **GPU 경로(헤드리스 Chromium + ANGLE Metal, 이 머신의 M2 Pro)에서 three.js `InstancedMesh`는 강체 200, 1,000, 5,000개 모두 60 Hz 포즈 스트림을 받아 rAF 59.99~60.12 fps(3회 모두)로 그렸다.** 프레임 간격 p99 16.67 ms, 33.0 ms 넘는 간격 0(9회 실행의 원자료 간격 전수). 렌더 한 프레임을 GPU 완료까지 기다린 시간(`readPixels`)은 5,000개에서도 중앙값 0.69 ms(약 1,230 프레임/s)여서 60 fps 상한(vsync)이 한계가 아니다. 다만 그려진 서로 다른 틱은 실행마다 46~60 /s로 흔들렸고(아래 "그리기 전에 교체된 프레임"), 5,000개에서도 같은 크기였다.
- **소프트웨어 래스터라이저(SwiftShader, 기본 헤드리스)는 이번 3회에서 200개 33.9 fps(21~56), 1,000개 14.6 fps(9.5~24.7), 5,000개 3.8 fps(1.5~4.4)**(중앙값과 범위). 이 값은 **실제 GPU의 프레임률이 아니다.** CPU로 삼각형을 채우는 비용이고, 같은 코드가 실행마다 2~3배 달랐다(아래 "한계"). 그래서 rAF 프레임률과 프레임당 JS(CPU) 시간(포즈 → 행렬 + `render()` 호출) 중앙값을 같이 적는다: SwiftShader 0.115 / 0.125 / 0.21 ms, Metal 0.115 / 0.12 / 0.16 ms.
- **대역폭은 인코딩이 정한다.** 이 스파이크의 인코딩(전 강체, 강체당 위치 3 + 쿼터니언 4 float32, 머리 24 B)에서 프레임은 5,624 / 28,024 / 140,024 B이고 60 Hz에서 **2.70 / 13.45 / 67.21 Mbit/s**다(계산값. Metal 실행에서 클라이언트가 실제로 받은 값 2.699 / 13.450 / 67.202 Mbit/s와 같다). 같은 프레임의 gzip·brotli는 원본의 약 94 %로 거의 줄지 않았다. 10분 스트림은 0.20 / 1.01 / 5.04 GB다. Chrome DevTools의 Fast 4G 프로파일(9 Mbit/s의 90 %)에는 200개만 들어간다(계산, 스로틀 아래에서 스트림을 돌려 보지 않았다). 인코딩 대안(양자화, 변화분, 관심 영역)은 재지 않았다.
- **조종 입력 → 화면 반영 지연(Metal, 루프백, 합성 코어)은 중앙값 26.9 / 27.4 / 27.6 ms, p95 34.4 / 35.5 / 35.0 ms**(200 / 1,000 / 5,000개, 3회 실행의 중앙값, 실행마다 40회, 9회 실행 모두 40/40 측정, 대체 0, 보이는 변화 없음 0). 최소 18.3 ms, 최대 54.0 ms. 절반 이상이 60 Hz 두 번의 정렬 대기(코어의 다음 틱, 화면의 다음 rAF)다. SwiftShader에서는 200개 51.2 ms(실행별 197.8 / 51.2 / 36.4), 1,000개는 실행별 2,848 / 4,752 / 267 ms인데 표본이 40회 중 11 / 10 / 33개뿐이고(나머지는 대체되었거나 보이는 변화 없음), 5,000개는 6개(한 실행)만 측정되어 17,321 ms다. 이 값도 GPU 값이 아니다.
- 이 측정이 보이지 않는 것: **코어 쪽 실제 비용**(MuJoCo 스텝, A0-01a의 실시간 배속은 200개에서도 0.02~0.03이다), 실제 네트워크, 실제 디스플레이 출력 지연, 다른 GPU·브라우저. 포즈는 MuJoCo가 아니라 결정론적 합성 생성기가 만든다. 즉 "웹 클라이언트가 포즈 스트림을 그리는 데 병목인가"에 답할 뿐 "코어가 실시간으로 낼 수 있는가"에는 답하지 않는다.
- 모든 속도·지연 값은 **[추정: 한 머신, 한 시점, 다른 시점·머신 재측정은 확인 필요]** 다. 이번 값은 부하 평균 21~43에서 쟀다(다른 에이전트의 작업이 동시에 돌았다). 앞선 측정 두 번(커밋 `0f56498`: 부하 38~75, 커밋 `20de380`: 부하 6~16)과 SwiftShader 값이 크게 달랐다(1,000개: 약 20 → 약 48 → 14.6 fps). 그 사이에 **클라이언트 코드와 부하가 둘 다 바뀌어서** 차이의 원인을 어느 한쪽으로 가르지 못한다. Metal 값은 세 번의 측정에서 모두 같은 자릿수였다.
- 흐름 제어(수신 적체)는 이 이슈 밖에서 발견한 문제로 #420에 넘겼다.

| 프레임 인코딩 `KPF-spike-1` | little-endian, 틱마다 메시지 1개, 모든 강체를 매번(`client-adapter.md` 3.3절 S1 범위). `u32 tick, u32 n, f64 sim_time_s, u32 ctrl_state, u32 ctrl_seq`(24 B) + 강체당 `f32 x y z [m]`(+Z 위), `f32 qx qy qz qw`(단위 쿼터니언) = 28 B. 프레임 = 24 + 28 n B. **C-05b의 스키마가 아니다**: 측정용으로 바이트를 고정했을 뿐이다 (`src/frame.js`) |
| 조종 입력 | 페이지에서 Space 키 → 8 B 이진 메시지(`u32 seq, u32 state`)를 서버로. 서버는 다음 틱에 마지막 입력 하나를 적용하고 프레임 머리에 `ctrl_state/ctrl_seq`로 돌려보낸다. 한 틱 안에 입력이 둘 이상 오면 서버는 최신 것만 적용한다 |
| 단계 | ① 예열 1.5 s ② **A**: 자연 rAF 루프 8 s(프레임률, 프레임 간격, 프레임당 CPU 시간, 대역폭) ③ **bench**: 같은 갱신 + 렌더를 연달아 60번, 매번 1픽셀 `readPixels`로 GPU 완료를 기다림(`gl.finish()`는 이 빌드에서 마이크로초 만에 돌아와 쓰지 않았다) ④ **지연**: 러너가 Playwright `keyboard.press("Space")`를 40번(간격 180~250 ms로 틱과 위상을 흩음) |
| 프레임당 CPU 시간 | rAF 콜백 안에서 `performance.now()`로 잰 `포즈 → 인스턴스 행렬` 시간과 `renderer.render()` 호출 시간. GPU 프로세스·래스터라이즈는 들어가지 않는다(비동기). 래스터 비용은 bench의 동기 프레임 시간이 보여준다 |
| 지연 표본 규칙 | 시작 = 키 이벤트의 `event.timeStamp`. 끝 = 마법색 상자가 **새 위치에 그려지고 이전 위치에서 사라진** 프레임의 `readPixels`. **표본은 그려진 프레임이 실어 온 `ctrl_seq`와 같은 입력 하나뿐이다**(그 입력의 최초 수신 시각과 상태 확인). 그려진 프레임의 `ctrl_seq`보다 작은 대기 입력은 코어가 이미 다른 입력으로 대체한 것이라 화면에 자기 변화로 나타난 적이 없다: 표본이 아니라 `superseded`로 따로 센다. 입력마다 `measured`(표본) / `superseded`(대체) / `no_visible_change`(보이는 변화 없음) / `unresolved` 넷 중 정확히 하나로 끝나서 `requested`와 맞는다(결과 JSON 18개 실행(6파일 × 3규모) 전부 확인: 합이 40). `unresolved`는 마지막 입력 뒤 최대 4 s를 더 기다린 시점에도 어떤 그려진 프레임이 그 입력을 확인해 주지 않은 입력이다. **4 s는 이 마지막 대기에만 쓰이고 표본의 상한이 아니다**: 입력 도중 4 s를 넘게 걸려도 나중에 그려지면 표본이다(SwiftShader 5,000개 최대 약 21 s). SwiftShader 5,000개 run1의 `unresolved` 40은 8 s 측정 동안 그려진 프레임이 18개뿐이라 어떤 입력도 확인되지 않은 경우다. 겹친 입력의 규칙은 `src/latency.js`(`LatencyTracker`)이고 `tests/latency.test.mjs`가 단언한다 구간: 입력 → 핸들러 / 핸들러 → 전송 / 전송 → 그 입력을 담은 첫 프레임 수신 / 수신 → 그리기 시작(다음 rAF 대기) / 그리기 시작 → 픽셀 확인 |
| 그리기 전에 교체된 프레임 | 새 프레임이 도착했을 때 직전에 받은 프레임이 아직 한 번도 그려지지 않았으면 센다. 일관성 점검: `frames_received = distinct_ticks_drawn + frames_overwritten_before_draw + frames_unaccounted`(미계정은 창 경계의 ±1) |

읽는 법:
- **rAF 59.99는 vsync 상한이다**(A0-01b와 같다). 한계가 아니다. Metal의 한계 여유는 동기 프레임 시간(5,000개 0.69 ms)이 말한다: 그 값은 rAF를 기다리지 않고 GPU 완료까지 연달아 돌린 값이고 16.7 ms 예산의 약 4 %다.
- **그리기 전에 교체된 프레임이 Metal에서도 실행마다 0~110개로 크게 흔들린다**(200개 run1 110개, 1,000개 run2 78개, 5,000개 run3 41개). 서버의 `setTimeout` 틱과 rAF가 둘 다 60 Hz라 위상이 맞는 구간에는 0이고, 어긋나는 구간에는 한 rAF 사이에 프레임 둘이 도착해 하나가 교체된다 [추정: 두 시계의 맥놀이]. 어느 규모에서든 생기고 규모에 비례하지 않아서 렌더 비용이 원인은 아니다. 클라이언트에 지터 버퍼(받은 프레임을 한 틱 늦춰 그리기)가 없다. 필요한지는 이 측정의 범위 밖이다. (수신 − 그려진 틱 − 교체 = 미계정은 실행마다 −1~1로 창 경계의 오차다.)
- **SwiftShader 숫자는 제품의 프레임률이 아니다.** 같은 코드가 GPU 경로에서 1,164~1,793 프레임/s이므로 SwiftShader의 느림은 삼각형을 CPU로 채우는 비용이다. JS 쪽 시간은 두 경로에서 같은 자릿수(0.1~0.2 ms)다.
- SwiftShader에서는 렌더가 프레임 도착을 못 따라가 클라이언트 메인 스레드가 메시지를 받는 속도가 떨어지고(1,000개 44.96 /s, 5,000개 2.2 /s) 서버는 틱을 건너뛰었다. 루프백 TCP 버퍼가 크기 때문에 서버의 `bufferedAmount` 한도(프레임 3개)만으로는 적체를 막지 못한다. 실제 클라이언트에는 수신 확인(ack) 기반 흐름 제어나 오래된 프레임 버리기가 필요하다는 관찰이다. 이 이슈의 DoD 밖이라 구현하지 않았고 **#420 "[A0-02a-f] 포즈 스트림 흐름 제어"** 로 등록했다.

### 알려진 한계 (정직성)

- 실행 3회씩이다. 한 머신, 한 시점(부하 21~43, 다른 에이전트 작업과 동시)의 값이고 다른 시점의 재측정은 [확인 필요]다. 실행 간 분산은 표의 `[ / / ]`에 있다. SwiftShader는 같은 코드가 실행마다 2~3배 달랐고 앞선 두 측정과도 크게 달랐다. Metal은 세 측정 모두 같은 자릿수였다.
- 헤드리스 Chromium의 ANGLE Metal 경로다. 보이는 창, 백그라운드 탭 스로틀, 다른 GPU(Intel, NVIDIA, 모바일), Firefox, Safari, Windows는 재지 않았다. 헤드리스 rAF는 화면 주사율이 아니라 60 Hz 가상 프레임 펄스를 따를 수 있다 [추정, 확인 필요].
- 코어는 합성 생성기다(결과 JSON `server.frame_build_ms`). MuJoCo가 실제로 이 포즈를 실시간으로 낼 수 있는지는 A0-01a가 다루고 아직 열린 질문이다(`client-adapter.md` 4절).
- 장면은 단순 상자(Lambert, 그림자 없음)다. 실제 glb 메시, 텍스처, 그림자, 후처리, 물체별 커스텀 재질은 재지 않았다. 5,000개 모두 같은 지오메트리·드로 콜 1개라 서로 다른 메시 5,000개와는 비교할 수 없다.
- 클라이언트는 최신 프레임 하나만 그린다(보간·지터 버퍼 없음, F4의 두 프레임 사이 보간 미구현). 그리기 전에 교체된 프레임 수와 틱 간격은 JSON에 있다.
- 지연 합계는 루프백 값이다. 실제 네트워크 왕복은 더해야 한다. 스로틀 아래 지연은 재지 않았다.
- `ws`의 `perMessageDeflate`는 껐다. 압축된 WebSocket은 재지 않았다(프레임 압축률이 94 %라 이득이 작을 것이다 [추정]).
- 새 이슈: #420(포즈 스트림 흐름 제어).
