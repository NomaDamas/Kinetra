# 웹 클라이언트 스케일과 공유 링크 (A0-02)

측정만 한다. 최적화하지 않았다. `spikes/mujoco-limits/REPORT.md`, `spikes/mujoco-wasm/REPORT.md`와 같은 규칙(시드 고정, 부하 기록, 값마다 명령과 머신)을 따른다. 이 파일은 A0-02의 하위 이슈가 각자 자기 절만 채운다.

## A0-02a. 렌더와 실행 스트림 스케일 (이슈 #47)

### 결론 먼저

- **GPU 경로(헤드리스 Chromium + ANGLE Metal, 이 머신의 M2 Pro)에서 three.js `InstancedMesh`는 강체 200, 1,000, 5,000개 모두 60 Hz 포즈 스트림을 받아 rAF 59.99~60.12 fps(3회 모두)로 그렸다.** 프레임 간격 p99 16.67 ms, 33.0 ms 넘는 간격 0(9회 실행의 원자료 간격 전수). 렌더 한 프레임을 GPU 완료까지 기다린 시간(`readPixels`)은 5,000개에서도 중앙값 0.69 ms(약 1,230 프레임/s)여서 60 fps 상한(vsync)이 한계가 아니다. 다만 그려진 서로 다른 틱은 실행마다 46~60 /s로 흔들렸고(아래 "그리기 전에 교체된 프레임"), 5,000개에서도 같은 크기였다.
- **소프트웨어 래스터라이저(SwiftShader, 기본 헤드리스)는 이번 3회에서 200개 33.9 fps(21~56), 1,000개 14.6 fps(9.5~24.7), 5,000개 3.8 fps(1.5~4.4)**(중앙값과 범위). 이 값은 **실제 GPU의 프레임률이 아니다.** CPU로 삼각형을 채우는 비용이고, 같은 코드가 실행마다 2~3배 달랐다(아래 "한계"). 그래서 rAF 프레임률과 프레임당 JS(CPU) 시간(포즈 → 행렬 + `render()` 호출) 중앙값을 같이 적는다: SwiftShader 0.115 / 0.125 / 0.21 ms, Metal 0.115 / 0.12 / 0.16 ms.
- **대역폭은 인코딩이 정한다.** 이 스파이크의 인코딩(전 강체, 강체당 위치 3 + 쿼터니언 4 float32, 머리 24 B)에서 프레임은 5,624 / 28,024 / 140,024 B이고 60 Hz에서 **2.70 / 13.45 / 67.21 Mbit/s**다(계산값. Metal 실행에서 클라이언트가 실제로 받은 값 2.699 / 13.450 / 67.202 Mbit/s와 같다). 같은 프레임의 gzip·brotli는 원본의 약 94 %로 거의 줄지 않았다. 10분 스트림은 0.20 / 1.01 / 5.04 GB다. Chrome DevTools의 Fast 4G 프로파일(9 Mbit/s의 90 %)에는 200개만 들어간다(계산, 스로틀 아래에서 스트림을 돌려 보지 않았다). 인코딩 대안(양자화, 변화분, 관심 영역)은 재지 않았다.
- **조종 입력 → 화면 반영 지연(Metal, 루프백, 합성 코어)은 중앙값 26.9 / 27.4 / 27.6 ms, p95 34.4 / 35.5 / 35.0 ms**(200 / 1,000 / 5,000개, 3회 실행의 중앙값, 실행마다 40회, 9회 실행 모두 40/40 측정, 대체 0, 보이는 변화 없음 0). 최소 18.3 ms, 최대 54.0 ms. 절반 이상이 60 Hz 두 번의 정렬 대기(코어의 다음 틱, 화면의 다음 rAF)다. SwiftShader에서는 200개 51.2 ms(실행별 197.8 / 51.2 / 36.4), 1,000개는 실행별 2,848 / 4,752 / 267 ms인데 표본이 40회 중 11 / 10 / 33개뿐이고(나머지는 대체되었거나 보이는 변화 없음), 5,000개는 6개(한 실행)만 측정되어 17,321 ms다. 이 값도 GPU 값이 아니다.
- 이 측정이 보이지 않는 것: **코어 쪽 실제 비용**(MuJoCo 스텝, A0-01a의 실시간 배속은 200개에서도 0.02~0.03이다), 실제 네트워크, 실제 디스플레이 출력 지연, 다른 GPU·브라우저. 포즈는 MuJoCo가 아니라 결정론적 합성 생성기가 만든다. 즉 "웹 클라이언트가 포즈 스트림을 그리는 데 병목인가"에 답할 뿐 "코어가 실시간으로 낼 수 있는가"에는 답하지 않는다.
- 모든 속도·지연 값은 **[추정: 한 머신, 한 시점, 다른 시점·머신 재측정은 확인 필요]** 다. 이번 값은 부하 평균 21~43에서 쟀다(다른 에이전트의 작업이 동시에 돌았다). 앞선 측정 두 번(커밋 `0f56498`: 부하 38~75, 커밋 `20de380`: 부하 6~16)과 SwiftShader 값이 크게 달랐다(1,000개: 약 20 → 약 48 → 14.6 fps). 그 사이에 **클라이언트 코드와 부하가 둘 다 바뀌어서** 차이의 원인을 어느 한쪽으로 가르지 못한다. Metal 값은 세 번의 측정에서 모두 같은 자릿수였다.
- 흐름 제어(수신 적체)는 이 이슈 밖에서 발견한 문제로 #420에 넘겼다.

| 단계 | ① 예열 1.5 s ② **A**: 자연 rAF 루프 8 s(프레임률, 프레임 간격, 프레임당 CPU 시간, 대역폭) ③ **bench**: 같은 갱신 + 렌더를 연달아 60번, 매번 1픽셀 `readPixels`로 GPU 완료를 기다림(`gl.finish()`는 이 빌드에서 마이크로초 만에 돌아와 쓰지 않았다) ④ **지연**: 러너가 Playwright `keyboard.press("Space")`를 40번(간격 180~250 ms로 틱과 위상을 흩음) |
| 프레임당 CPU 시간 | rAF 콜백 안에서 `performance.now()`로 잰 `포즈 → 인스턴스 행렬` 시간과 `renderer.render()` 호출 시간. GPU 프로세스·래스터라이즈는 들어가지 않는다(비동기). 래스터 비용은 bench의 동기 프레임 시간이 보여준다 |
| 지연 표본 규칙 | 시작 = 키 이벤트의 `event.timeStamp`. 끝 = 마법색 상자가 **새 위치에 그려지고 이전 위치에서 사라진** 프레임의 `readPixels`. **표본은 그려진 프레임이 실어 온 `ctrl_seq`와 같은 입력 하나뿐이다**(그 입력의 최초 수신 시각과 상태 확인). 그려진 프레임의 `ctrl_seq`보다 작은 대기 입력은 코어가 이미 다른 입력으로 대체한 것이라 화면에 자기 변화로 나타난 적이 없다: 표본이 아니라 `superseded`로 따로 센다. 입력마다 `measured`(표본) / `superseded`(대체) / `no_visible_change`(보이는 변화 없음) / `unresolved` 넷 중 정확히 하나로 끝나서 `requested`와 맞는다(결과 JSON 18개 실행(6파일 × 3규모) 전부 확인: 합이 40). `unresolved`는 마지막 입력 뒤 최대 4 s를 더 기다린 시점에도 어떤 그려진 프레임이 그 입력을 확인해 주지 않은 입력이다. **4 s는 이 마지막 대기에만 쓰이고 표본의 상한이 아니다**: 입력 도중 4 s를 넘게 걸려도 나중에 그려지면 표본이다(SwiftShader 5,000개 최대 약 21 s). SwiftShader 5,000개 run1의 `unresolved` 40은 8 s 측정 동안 그려진 프레임이 18개뿐이라 어떤 입력도 확인되지 않은 경우다. 겹친 입력의 규칙은 `src/latency.js`(`LatencyTracker`)이고 `tests/latency.test.mjs`가 단언한다 구간: 입력 → 핸들러 / 핸들러 → 전송 / 전송 → 그 입력을 담은 첫 프레임 수신 / 수신 → 그리기 시작(다음 rAF 대기) / 그리기 시작 → 픽셀 확인 |

읽는 법:
- **rAF 59.99는 vsync 상한이다**(A0-01b와 같다). 한계가 아니다. Metal의 한계 여유는 동기 프레임 시간(5,000개 0.69 ms)이 말한다: 그 값은 rAF를 기다리지 않고 GPU 완료까지 연달아 돌린 값이고 16.7 ms 예산의 약 4 %다.
- **그리기 전에 교체된 프레임이 Metal에서도 실행마다 0~110개로 크게 흔들린다**(200개 run1 110개, 1,000개 run2 78개, 5,000개 run3 41개). 서버의 `setTimeout` 틱과 rAF가 둘 다 60 Hz라 위상이 맞는 구간에는 0이고, 어긋나는 구간에는 한 rAF 사이에 프레임 둘이 도착해 하나가 교체된다 [추정: 두 시계의 맥놀이]. 어느 규모에서든 생기고 규모에 비례하지 않아서 렌더 비용이 원인은 아니다. 클라이언트에 지터 버퍼(받은 프레임을 한 틱 늦춰 그리기)가 없다. 필요한지는 이 측정의 범위 밖이다. (수신 − 그려진 틱 − 교체 = 미계정은 실행마다 −1~1로 창 경계의 오차다.)
- **SwiftShader 숫자는 제품의 프레임률이 아니다.** 같은 코드가 GPU 경로에서 1,164~1,793 프레임/s이므로 SwiftShader의 느림은 삼각형을 CPU로 채우는 비용이다. JS 쪽 시간은 두 경로에서 같은 자릿수(0.1~0.2 ms)다.
- SwiftShader에서는 렌더가 프레임 도착을 못 따라가 클라이언트 메인 스레드가 메시지를 받는 속도가 떨어지고(1,000개 44.96 /s, 5,000개 2.2 /s) 서버는 틱을 건너뛰었다. 루프백 TCP 버퍼가 크기 때문에 서버의 `bufferedAmount` 한도(프레임 3개)만으로는 적체를 막지 못한다. 실제 클라이언트에는 수신 확인(ack) 기반 흐름 제어나 오래된 프레임 버리기가 필요하다는 관찰이다. 이 이슈의 DoD 밖이라 구현하지 않았고 **#420 "[A0-02a-f] 포즈 스트림 흐름 제어"** 로 등록했다.

### 알려진 한계 (정직성)

- 실행 3회씩이다. 한 머신, 한 시점(부하 21~43, 다른 에이전트 작업과 동시)의 값이고 다른 시점의 재측정은 [확인 필요]다. 실행 간 분산은 표의 `[ / / ]`에 있다. SwiftShader는 같은 코드가 실행마다 2~3배 달랐고 앞선 두 측정과도 크게 달랐다. Metal은 세 측정 모두 같은 자릿수였다.
- 헤드리스 Chromium의 ANGLE Metal 경로다. 보이는 창, 백그라운드 탭 스로틀, 다른 GPU(Intel, NVIDIA, 모바일), Firefox, Safari, Windows는 재지 않았다. 헤드리스 rAF는 화면 주사율이 아니라 60 Hz 가상 프레임 펄스를 따를 수 있다 [추정, 확인 필요].
- 코어는 합성 생성기다(결과 JSON `server.frame_build_ms`). MuJoCo가 실제로 이 포즈를 실시간으로 낼 수 있는지는 A0-01a가 다루고 아직 열린 질문이다(`client-adapter.md` 4절).
- 장면은 단순 상자(Lambert, 그림자 없음)다. 실제 glb 메시, 텍스처, 그림자, 후처리, 물체별 커스텀 재질은 재지 않았다. 5,000개 모두 같은 지오메트리·드로 콜 1개라 서로 다른 메시 5,000개와는 비교할 수 없다.
- 클라이언트는 최신 프레임 하나만 그린다(보간·지터 버퍼 없음, F4의 두 프레임 사이 보간 미구현). 그리기 전에 교체된 프레임 수와 틱 간격은 JSON에 있다.
- 지연 합계는 루프백 값이다. 실제 네트워크 왕복은 더해야 한다. 스로틀 아래 지연은 재지 않았다.
- `ws`의 `perMessageDeflate`는 껐다. 압축된 WebSocket은 재지 않았다(프레임 압축률이 94 %라 이득이 작을 것이다 [추정]).
- 새 이슈: #420(포즈 스트림 흐름 제어).

### 결론 먼저

- **예시 리플레이 번들(로켓 자동차 1대 + 바퀴 4개, 4.5 s, 1,126프레임)의 데이터는 `poses.bin` 157,640 B + `bundle.json` 3,063 B = 160,703 B(원본)이고 gzip(9) 124,103 B, brotli(11) 120,646 B다.** 포즈는 float32 그대로라 압축이 거의 안 된다(brotli 75 %). 페이지 전체(HTML + three.js 일부를 포함해 줄인 스크립트 + 데이터 2개)는 원본 703,278 B → gzip 260,478 B → brotli 233,089 B이다. **전송량의 절반가량(brotli 기준 112,205 B)은 three.js를 포함한 스크립트이고 데이터가 아니다.**
- **링크 열기 → 첫 프레임(첫 `render()` + `readPixels` 완료, 차체 픽셀 확인 통과) 중앙값(5회, 서버가 미리 압축한 gzip / brotli)**: 무제한 145 / 143 ms(SwiftShader), 71 / 59 ms(Metal GPU); Fast 4G 914 / 890 ms(SwiftShader), 811 / 794 ms(Metal); Slow 4G 3,290 / 3,122 ms(SwiftShader), 3,207 / 3,049 ms(Metal); Slow 3G 11,399 / 10,808 ms(SwiftShader), 11,299 / 10,712 ms(Metal). 압축이 없으면 Fast 4G 1,361(SwiftShader) / 1,259(Metal) ms, Slow 4G 5,764 / 5,676 ms, Slow 3G 20,260 / 20,166 ms.
- **스로틀 아래 시간은 거의 전부 전송이다.** 첫 프레임 − 데이터 도착(`fetched`)은 SwiftShader 약 20~30 ms, Metal 약 13~25 ms다. 스로틀 칸의 두 경로 차이(약 50~100 ms)는 이 구간과 노이즈의 합이다. 무제한 칸은 두 경로 모두 수십~150 ms이고 이 칸에서 SwiftShader−Metal 차이(약 75~90 ms)가 소프트웨어 렌더의 비용으로 보인다 [추정].
- 스로틀 값은 Chrome DevTools 프리셋의 대역폭·지연을 CDP `Network.emulateNetworkConditions`로 넣은 것이다. 실제 이동통신 망, TLS 핸드셰이크, DNS, CDN, HTTP/2 다중화는 없다(루프백 HTTP/1.1).
- 이 절의 시간은 **서버가 모든 파일을 시작 전에 미리 압축한 뒤** 5회 쟀다. 처음 낸 값(3회, 커밋 `a50c1e2`)은 gzip·brotli 서버가 첫 요청에서 압축했다. 그 값에서 무제한 칸의 brotli 485 ms(3회 중 한 번 6.8 s)와 gzip 177 ms(SwiftShader)는 이 영향이 섞여 있었고, 지금 값(무제한 SwiftShader gzip 145 ms, brotli 143 ms, 위 표)이 대체한다. 지금 값은 Metal 실행 도중 부하가 올랐던 구간을 포함한다(아래).

- 번들 크기는 계산(결정론)이고 서버 로그의 실제 전송 바이트와 같다(gzip 260,478, brotli 233,089, 원본 703,278, 요청 4개).
- 데이터 비용: 4.5 s 한 대의 리플레이가 프레임당 140 B, 초당 약 35 kB(250 프레임/s × 140 B)다. 강체가 늘면 선형이다: **5,000개를 같은 프레임 수로 저장하면 1,126프레임 × 5,000강체 × 28 B = 157,640,000 B ≈ 157.6 MB**(원본, 압축이 거의 안 되는 float32). 강체 수 5개 → 5,000개는 1,000배라 160,703 B가 약 160 MB가 된다(같은 계산: 5 강체의 157,640 B × 1,000). 이 방식 그대로는 큰 장면의 공유 번들로 무겁고 양자화나 변화분, 낮은 저장 프레임률이 필요하다 [추정, 재지 않음].

### 알려진 한계 (정직성)

- 한 머신, 한 시점이고 부하가 15~120으로 실행 중에 크게 바뀌었다(위). 두 렌더 경로 모두 헤드리스 Chromium이다.
- 스로틀은 CDP 에뮬레이션이라 패킷 손실·혼잡·TCP 느린 시작·TLS·DNS를 재현하지 않는다. 서버는 루프백 HTTP/1.1이다. 실제 호스팅(CDN, HTTP/2·3)에서는 다르다.
- 콜드 로드만 쟀다(캐시 끔). 재방문(캐시), 서비스 워커, 모바일 CPU(스크립트 파싱 542 kB)는 재지 않았다.
- 번들은 5개 강체의 4.5 s 한 건이다. 실제 공유 번들(glTF 메시, 텍스처, 이벤트)의 크기는 H-03a가 정한다. 포즈 압축(양자화, 변화분)은 재지 않았다.
- 기록은 macOS arm64 MuJoCo 네이티브의 것이다. 플랫폼 간 비트 불일치(`spikes/mujoco-wasm/REPORT.md` 5.5절, #54)가 있으므로 이 번들은 "그 실행의 기록"이고 다른 플랫폼에서 재현 확인이 아니다. 화면에는 `1회 실행. 판정이 아닙니다`만 보이고 판정 문구는 없다.

## A0-02a-f. 포즈 스트림 흐름 제어 (이슈 #420)

### 결론 먼저

측정: 2026-11-11, 가드 아래, 같은 클라이언트 코드로 `flow=none`과 `flow=ack&win=2`를 SwiftShader·Metal 각각 3회(실행마다 1,000개와 5,000개 한 프로세스) 번갈아 쟀다. 부하 평균(1분)이 실행마다 8~110으로 크게 달랐고 **같은 실행 번호의 none과 ack도 부하가 같지 않다**(표의 "부하" 열). 그래서 아래는 "이 표본에서 보인 것"이지 효과의 크기 추정이 아니다.

- **SwiftShader 5,000개(렌더가 프레임 도착을 못 따르는 경우)에서는 ack가 입력 → 화면 지연을 줄였다.** none 4.2 s·2.5 s(두 실행, 한 실행은 40회 모두 4 s 안에 못 끝남), ack W=2 0.74 / 1.04 / 0.90 s(3회). A0-02a의 재측정(위 "결론 먼저")에서도 같은 조건의 지연은 수 초~17 s였다(표본 6개뿐). 처음 낸 3.3 s(부하가 낮던 시점)는 그 재측정으로 대체됐다. 그러나 **100 ms 문턱에는 한참 못 미친다**: 약 0.7~1.0 s가 남았다.
- **SwiftShader 1,000개에서는 부하에 따라 갈렸고 부하를 맞춘 비교가 아니다.** none 7.5 s·10.8 s(부하 20~44)·0.089 s(부하 20~24). ack 1.0 s(부하 46~49)·0.100 s·0.106 s(부하 17~110). 수 초 → 1 s 쪽으로 간 칸은 부하가 다르고, 적체가 없던 실행(none 0.089 s, ack 0.100/0.106 s)에서는 **차이가 없거나 ack가 조금 높다**(표본 40개, 분산 미측정).
- **Metal(GPU)에서는 ack 이득이 보이지 않는다.** 5,000개 none 27.0 / 27.7 / 26.9 ms, ack 30.1 / 29.0 / 31.1 ms. 3회 모두 ack가 2~4 ms 높았다(원인은 모른다 [추정: ack 한 건을 매 그리기마다 보내는 일과 코어가 틱을 건너뛰어 틱 대기가 달라지는 것, 재지 않았다]). 1,000개 none 505.7(부하 44, 표본 31/40)·27.9·28.6 ms, ack 30.5·28.4·28.1 ms. none 1회에서만 렌더가 밀렸고(부하 44~52, rAF 11 fps) 같은 부하의 ack 실행이 없어서 그 칸은 비교할 수 없다.
- **ack는 적체를 "건너뛴 틱"으로 바꾼다.** 코어가 보냈지만 ack를 못 받은 프레임은 모든 ack 실행에서 최대 2개(`W`)였다. SwiftShader 5,000개에서 받은 틱 간격 중앙값은 none 1(밀린 프레임을 틱 순서대로 받음)에서 ack 10(약 167 ms마다 최신 틱)으로 바뀌었다. **그려지는 틱 수는 늘지 않았다**(ack 6.2~7.0 /s, none 0.9~9.2 /s): 렌더 속도가 한계이고 ack가 그것을 올리지는 못한다.
- 한 실행(SwiftShader ack, 5,000개, 부하 49~50)은 페이지가 3분 안에 끝나지 않아 5,000개 결과가 없다(1,000개는 있다). 같은 조건의 none 실행도 5,000개에서 40회 모두 미해결(0/40)이었다. ack 5,000개는 부하 8로 한 번 더 쟀다(run4).
- 이 결과는 합성 코어, 루프백, 헤드리스 Chromium, 한 머신, 실행당 40표본이다. [추정] 요약: ack는 "클라이언트가 렌더에 묶여 메시지를 못 받는" 상황의 지연을 줄이지만 100 ms를 지키게 하지는 못한다.

### 무엇을 같은 측정 페이지에 넣었나

| 모드 | 코어(`src/stream.mjs`) | 클라이언트(`src/client-pose.js`) |
|---|---|---|
| `flow=none` (A0-02a와 같은 동작, 기본) | `bufferedAmount`가 프레임 3개를 넘으면 그 틱을 건너뛴다(`backpressure_skipped`) | ack를 보내지 않는다 |
| `flow=ack&win=W` | **보냈지만 ack가 안 온 프레임이 W개면 그 틱을 건너뛴다**(`window_skipped`). 건너뛴 틱은 쌓지 않으므로 슬롯이 비면 보내는 프레임은 항상 **그 순간의 최신 틱**이다("최신 프레임 우선"). `bufferedAmount`는 보지 않는다 | 새 틱을 그릴 때마다(`render()` 직후) 그 틱 번호를 담은 ack 8 B를 보낸다. 같은 프레임을 다시 그려도 ack는 한 번이다 |

- 규칙은 `src/flow.js`(`AckWindow`: 코어, `AckSender`: 클라이언트)에 있다. **ack는 누적이다**: 틱 T의 ack는 T 이하로 보낸 프레임 전부를 받은 것으로 친다(코어가 건너뛴 틱 사이의 번호도 된다). 보낸 적 없는 틱, 이미 ack한 틱 이하, 정수가 아닌 값은 버리고 `acks_ignored`로 센다.
- 클라이언트 → 코어 메시지에 종류 필드가 생겼다(`src/frame.js`): 조종 12 B(`u32 kind=1, seq, state`), ack 8 B(`u32 kind=2, tick`). A0-02a의 8 B 조종 메시지(종류 없음)는 없어졌다. **C-05b의 스키마가 아니다.** 알아볼 수 없는 메시지는 `bad_messages`로 세고 연결을 끊지 않는다.
- 조종 입력은 ack와 무관하게 받는다. 창이 가득 차도 조종 메시지는 다음 틱에 적용되고 다음에 실제로 나가는 프레임에 실린다(`tests/stream.test.mjs`가 단언).
- URL: `/?n=5000&flow=ack&win=2`. 서버는 `flow`가 `none|ack`가 아니거나 `win`이 1~16 정수가 아니면 연결을 거절한다.
- 러너: `FLOW=ack WIN=2 GL=swiftshader|metal`. 결과 JSON은 `flow`, `win`을 담고 서버 쪽에 `window_skipped`, `acks`, `acks_ignored`, `ack_lag_ms`(보낸 뒤 ack가 코어에 닿기까지), `inflight_at_tick`(틱마다 안 받은 프레임 수)가, 클라이언트 쪽에 `net.recv_tick_gap`(받은 프레임의 틱 간격. 1이면 틱을 빠짐없이 받음), `net.acks_sent`가 새로 들어갔다. 스크린샷은 `pose-<gl>-ack<W>-<n>.png`로 A0-02a의 것을 덮어쓰지 않는다. `summarize-pose.mjs swiftshader-ack2`가 표를 만든다.

### 단위 시험으로 확인한 것 (`pnpm --dir spikes/web-client test`, 32개 통과)

`tests/flow.test.mjs`, `tests/stream.test.mjs`(실제 WebSocket, 실행 시간은 100~400 ms 단위):
- ack를 안 보내는 클라이언트는 `win`개 프레임(틱 0..W-1)만 받고 코어는 이후 틱을 건너뛴다(쌓지 않는다).
- ack 한 번이 슬롯을 비우고 그 뒤 첫 프레임은 **다음 번호가 아니라 최신 틱**이다(300 ms 뒤 틱 18 이상).
- 보낸 적 없는 틱, 반복, 더 오래된 틱, 크기가 틀린 메시지는 상태를 바꾸지 않고 연결도 끊지 않는다.
- 창이 가득 찬 동안에도 조종 메시지가 다음 프레임에 실린다. `flow=none`은 ack를 무시한다.
- 이것은 **메커니즘이 설계대로 동작하는지**이다. 지연이 줄었다는 증거가 아니다.

- SwiftShader 1,000개 none run1·run2와 5,000개 모든 none·ack 실행은 표본의 상당수가 대체되거나(`superseded`) 변화 없음으로 빠진다. 남은 표본(예: 9/40, 4/40)의 중앙값은 **적체가 가장 심할 때를 덜 대표하거나 더 대표할 수 있다** [추정]. 5,000개 none run1은 40회 모두 4 s 안에 끝나지 않아 지연 값이 없다(그 칸의 실제 지연은 4 s 이상이다).

- 받은 틱 간격이 큰 것(SwiftShader 5,000개 ack 10틱 = 약 167 ms)은 클라이언트가 보간해야 하는 간격이다. 틱이 연속이 아니다.
- Metal 5,000개 ack run1(부하 34~35): rAF 42 fps, 틱 간격 최대 60. 같은 구간의 none run1(부하 36)도 28.6 fps였다. 두 모드 모두 이 실행에서 렌더가 밀렸고 지연 중앙값은 둘 다 30 ms 이하였다(밀린 구간은 입력 표본에 안 걸렸거나 짧았다).

| C-05b 쟁점 | 이 스파이크가 말하는 것 | 근거 상태 |
|---|---|---|
| 프레임 프로토콜에 클라이언트 → 코어 ack(마지막으로 그린 틱)를 둘 수 있게 틈을 남기는가 | **남긴다.** 필요성: ack 없이 서버의 `bufferedAmount` 한도만 쓰면 렌더가 밀린 클라이언트의 지연이 수 초가 됐다(A0-02a 재측정 5,000개 17.3 s(표본 6개), 이번 none 2.5~10.8 s, 서버가 건너뛴 틱 1,700~7,200개가 막지 못함). 효과: SwiftShader 5,000개에서 ack W=2는 0.74~1.04 s로 줄였다. 비용: 8 B × 60/s = 480 B/s(계산). **한계: ack만으로 100 ms를 지키지는 못한다**(0.74 s 남음). 렌더가 밀리지 않는 GPU 경로에서는 지연이 줄지 않았고 2~4 ms 늘었다 | 필요성·효과: 측정(SwiftShader 5,000개 3회 + none 2회, 부하 불일치). Metal 무효과: 측정(3회). 비용: 계산 |
| 코어가 건너뛰는 틱을 프로토콜이 허용하는가 | 허용해야 한다. ack 아래에서 SwiftShader 5,000개의 받은 틱 간격은 중앙값 10(약 167 ms), 1,000개는 중앙값 1이고 p99 3~26, 최대 51이다. 클라이언트는 `tick`으로 보간하거나 재생해야 하고 "매 틱 도착"을 가정하면 안 된다 | 측정(받은 틱 간격) |
| 창 크기 W | **W=2만 쟀다.** 안 받은 프레임은 2개를 넘지 않았다(설계대로). W가 지연에 주는 영향은 재지 않았다 [확인 필요]. 협상값인지 코어가 적응시키는 값인지는 정하지 않는다 | W=2: 측정. 다른 W: 미측정 |
| 서버 쪽 한도(ack 없음)만으로 충분한가 | 아니다(위 첫 행). 원격 연결에서는 TCP가 `bufferedAmount`를 올릴 수 있어 다를 수 있다 [추정, 재지 않았다] | 측정(루프백) + 추정 |
| 입력 채널과 프레임 채널 분리 | 조종 메시지는 ack와 무관하게 받았고 창이 가득 차도 다음 프레임에 실렸다(단위 시험). 입력이 프레임 흐름 제어에 막히지 않는다는 요구는 프로토콜 쪽 결정으로 남겨 둘 수 있다 | 단위 시험 |
| 렌더 속도 자체 | ack는 그려지는 틱 수를 올리지 못했다(SwiftShader 5,000개 6~7 /s). 클라이언트 렌더 한계는 흐름 제어 밖의 문제다(장면 단순화, 렌더 간격 줄이기 등은 다루지 않았다) | 측정 |

효과가 측정된 곳은 "렌더가 밀린 클라이언트" 한 경우뿐이다. ack의 유무를 C-05b가 정할 때 이 결과는 "있으면 SwiftShader 5,000개에서 수 초 → 약 1 s" 이상을 말하지 않는다.

### 범위 밖과 한계

- 제품 UI, 실제 MuJoCo 코어, 인코딩 압축(양자화, 변화분)은 하지 않았다.
- 한 클라이언트, 루프백, 합성 코어다. 실제 네트워크 왕복, 여러 클라이언트, 브라우저 백그라운드 스로틀은 재지 않았다.
- "최신 프레임 우선"을 코어 쪽에서만 구현했다. 클라이언트 쪽에서 도착한 프레임 중 최신 것만 그리는 동작은 A0-02a에 이미 있다(`latest`).
- 새 의존성 없음(원장 행 없음).
