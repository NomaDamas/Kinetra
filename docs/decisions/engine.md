## 요약

**결정안 [제안]**

1. **S1 주 클라이언트는 웹(three.js/R3F + WebXR)이고, 화면의 물리는 코어의 실행을 그대로 재생한다**(`client-adapter.md` 4절의 구성 A).
2. **코어의 물리와 판정은 MuJoCo 네이티브(4.0.0으로 고정)다.** 판정은 여기서만 나온다.
3. **브라우저 MuJoCo WASM은 "미리보기"로만 쓴다**(X-05, 조건부). 판정을 만들지 않는다.
4. **Godot + Jolt는 S1에 시작하지 않는다.** S2의 조건부 두 번째 클라이언트 트랙(GD)으로 남기고, 6절의 조건이 측정으로 충족될 때만 연다.
5. **궤적 해시와 판정에는 플랫폼 태그를 붙이고, 기준 플랫폼을 하나로 고정한다**(5.4절). "재현 확인"은 태그가 같은 실행끼리만 말한다. 태그가 같으면 해시가 같다는 것은 아직 가정이고 #432가 검증한다.

**이 결정이 기대는 증거의 빈칸**(3.4절). 승인할 때 함께 보아야 한다.

- XR은 **에뮬레이터의 입력 경로까지만** 증거가 있다. 머지 전인 PR #437(A0-02b)에서 IWER 에뮬레이터 안의 `@pmndrs/xr` 컨트롤러로 부품 하나를 잡아 옮겼다(명령한 이동량 대비 최대 축 오차 7.15e-8 m). 헤드셋 프레임률은 [확인 필요]다(헤드셋이 없다). 스테레오 렌더와 손 추적은 하지 않았다.
- "S1은 강체 200개 실시간"은 미달로 나왔지만 부하가 심한 머신의 값이다. 한가한 머신의 재측정(#332)이 열려 있다.
- 웹 클라이언트의 수치(렌더, 입력 지연, 대역폭, 공유 링크, XR 에뮬레이터)는 **머지 전인 PR #415, #416, #437**의 값이다. 머지되며 바뀔 수 있다.
- GPU 수치는 헤드리스 Chromium의 ANGLE Metal(M2 Pro) 한 경로뿐이다. Godot 웹 내보내기와 XR 에뮬레이터는 소프트웨어 렌더러에서만 돌렸다.
- 고속 투사체(CB-02 #312)는 돌리지 않았다.

**기준.** 창업자의 기준은 "최종 버전에 도달할 수 있는 선택"이다. 어떤 단일 클라이언트도 일곱 가지 전부에서 가장 낫지 않으므로 계획은 엔진 하나를 고르는 대신 갈아 끼울 수 있는 경계(`client-adapter.md`)를 먼저 고정했다. 이 문서는 그 위에서 S1에 무엇을 쓰고 언제 두 번째 클라이언트를 여는지를 정한다.

**팀과 머신.** 팀은 1~2인 [추정]. S1은 12주다. 개발 머신은 Apple M2 Pro 한 대이고 측정 내내 다른 작업으로 바빴다(load average 6~217, 10코어). 그래서 속도 수치 대부분이 [추정]이다. 두 번째 클라이언트는 화면과 입력을 한 번 더 만드는 비용이다(계획 5.2절 [추정]).

## 2. 불변 결정

아래 넷은 이 문서가 바꾸지 않는다(계획 5.4절). 어떤 선택지를 고르든 지킨다.

1. **Project JSON이 원본이다.** 엔진 독립이고 코어에만 있다. MJCF는 컴파일 산출물이라 저장하지 않는다.
2. **모든 편집은 Command다.** 화면, XR, 음성, 에이전트, MCP가 같은 검증기를 거친다.
3. **판정은 코어의 MuJoCo 네이티브만 낸다.** 클라이언트의 물리(Jolt, 브라우저 WASM, 예측)는 판정의 입력이 되지 않는다.
4. **클라이언트는 어댑터 경계 뒤에 있다.** 다섯 계약(문서 구독, 명령 발행, 실행 스트림 프레임, 에셋 로딩, 입력 → Command)으로만 코어와 말한다.

함께 지키는 것: 안전선(계획 15.3절)은 엔진 선택과 무관하다. 대결 부품은 어떤 클라이언트에서도 내보내지 않고, 대결의 결과는 "게임 물리"로 표시한다.

이 문서가 더하자고 하는 것 [제안]: **5. 궤적 해시와 판정은 플랫폼 태그와 함께만 증거다**(5.4절).

### 4.2 결정안 [제안]

| # | 결정안 | 근거 |
|---|---|---|
| D1 | S1 주 클라이언트는 **웹(three.js/R3F + WebXR)**, 구성 A(코어 재생) | ① 모든 화면은 Claude Design 승인본에서 온다(창업자 결정, 계획 7절·12절: 승인본이 없는 화면 PR은 머지하지 않는다). 승인본은 HTML이라 React로 바로 옮긴다(`design/exports/`). ② 공유 링크가 brotli 233 kB, Fast 4G 약 0.8 s(Godot 웹은 brotli 약 7.2 MB). ③ S1에는 플레이와 판정이 갈리지 않는다. ④ GPU 경로에서 렌더는 단순 상자 5,000개까지 병목이 아니었다 |
| D2 | 코어의 물리와 판정은 **MuJoCo 네이티브**. 버전을 고정한다(지금 4.0.0) | 불변 결정 3. 같은 빌드·머신에서 모든 장면의 해시가 일치했다. 차량 한 대는 실시간의 약 800배다(부하 아래, `추정`). 물의 직접 힘이 수계산과 2.4×10⁻⁴ % 안에서 맞았다 |
| D3 | 브라우저 **MuJoCo WASM은 "미리보기"로만**. X-05의 착수 조건("A0-01b 통과")은 충족된 것으로 본다. 우선순위는 P2 그대로다 | 공식 바인딩이 네이티브와 같은 4.0.0 엔진이고, 로켓 자동차가 그대로 돌았으며, 차이를 수치로 냈다(최대 6.144e-6 m). 비트는 다르므로 판정이 될 수 없다. 바인딩은 스스로 WIP라고 적는다. 계획은 "통과"의 기준을 수치로 정하지 않았으므로 충족 여부는 창업자가 정한다(8.2절 6번) |
| D4 | **Godot + Jolt는 S1에 시작하지 않는다.** S2 조건부 트랙으로 유지한다 | Jolt도 부하 아래에서 문턱(1,000개 실시간)에 못 닿았다. 배속의 우위는 방향만 읽을 수 있다 [추정]. 화면·입력을 두 번 만드는 비용이 확실하고 이득은 미확인이다. 착수 조건은 6절 |
| D5 | **해시와 판정에 플랫폼 태그**를 붙이고 기준 플랫폼을 고정한다 | 5.4절 |
| D6 | 코어가 실시간에 못 미치는 장면에서 S1 클라이언트는 **받은 프레임을 느린 배속으로 재생하고 배속을 표시**한다. S1에 클라이언트 예측이나 자체 플레이 물리를 넣지 않는다 | `client-adapter.md` F2, F4. 예측을 넣는 순간 화면이 코어의 궤적이 아니게 된다(V1, V4) |

이 결정안의 약점(숨기지 않는다):

- 다물체 실시간은 MuJoCo의 약한 곳이다. 200개에서 부하 아래 0.02~0.03, CPU 시간 기준으로도 약 0.2였다. 한가한 머신에서도 1.0에 못 닿을 수 있다 [추정, #332가 잰다].
- XR은 에뮬레이터에서 입력이 들어와 부품이 움직인다는 것까지만 있다(PR #437, 머지 전). 헤드셋 프레임률, 스테레오 렌더, 손 추적의 측정이 없다(3.4절).
- 5,000개 모델의 컴파일이 42~47 s였다. 열린 세계 규모에서 "부품을 넣고 뺄 때마다 재컴파일"은 지금 방식으로는 감당할 수 없다. S1 규모(부품 200개에서 약 40 ms)에서는 문제가 되지 않는다 [추정: 부품 한 가지 모양, 부하 아래].
- 포즈 스트림은 인코딩을 그대로 두면 5,000개에서 67 Mbit/s다. 열린 세계에서는 부분 프레임이나 양자화가 있어야 한다.
- "최종 버전을 가두지 않는다"는 어댑터 경계에 기댄 설계상의 주장이다. S1에서 증명되는 것은 헤드리스 참조 클라이언트의 적합성 통과까지다(C-05c). Godot가 실제로 붙는지는 GD-01 전에는 [확인 필요]다.

### 4.3 포기한 것

- S1의 클라이언트 쪽 물리와 예측. 코어가 느리면 화면도 느리다.
- S1의 실시간 다물체 파괴(수백~수천 개).
- OpenXR 네이티브 XR. S1의 XR은 WebXR뿐이다.
- 코어 없이 다시 돌려 보는 공유 링크(X-05를 하지 않는 한).
- 설치 없는 제작. 코어가 로컬에서 돌아야 한다(계획 9절의 한계 그대로).
- 플랫폼과 무관한 궤적 해시(5.4절).

### 5.4 판정 해시의 권위 플랫폼 규칙 [제안]

**관찰한 것.** 아래 넷이 전부다. 머신은 둘뿐이다: 개발 머신 1대(Apple M2 Pro, macOS 15.6.1 arm64)와 GitHub `ubuntu-latest` 러너(x86-64).

1. **같은 머신·같은 빌드의 반복은 비트가 같았다.** 개발 머신에서: MuJoCo 네이티브 4.0.0 휠(A0-01a 장면별 2회. 200개·1,000개·결합 해제 장면은 별도 프로세스 2개도 같았고 5,000개는 같은 프로세스 안 2회뿐이다. A0-01b 23개 시나리오 2회, FL-01 2~3회), 같은 머신의 Chromium 안 WASM(21개 시나리오, 같은 페이지 2회와 별도 프로세스 3회), Godot + Jolt(5개 장면, 별도 프로세스 2회와 워커 1스레드). Linux 러너에서: 한 번의 러너 실행 안에서 기준 궤적을 두 번 만든 결과(궤적, 제어 해시, 궤적 해시). 테스트가 이 러너 안의 2회 일치를 단언한다.
2. **그 두 머신 사이는 비트가 다르다.** 같은 MuJoCo 4.0.0, 같은 모델과 제어인데 접촉 뒤 궤적이 다르다(최대 7.69e-4, 러너 1회). 시드에서 뽑은 제어 값도 마지막 비트가 달랐다.
3. **같은 머신에서 WASM과 네이티브는 비트가 다르다**(최대 6.144e-6 m).
4. **같은 머신·같은 빌드에서도 힘을 주는 경로가 다르면 해시가 다르다**(FL-01).

**관찰하지 않은 것.** 같은 OS·같은 아키텍처의 다른 머신 사이, 같은 이미지를 쓰는 다른 러너(다른 CPU 모델) 사이, 다른 날의 러너 실행 사이에서 해시가 같은지는 재지 않았다. 따라서 "같은 플랫폼이면 비트가 같다"는 일반 명제는 **관찰이 아니다.** 아래 규칙은 "플랫폼 태그가 같으면 궤적 해시가 같다"를 **가정 [제안]** 으로 두고, A0-05a #432가 검증한다 [확인 필요]. 검증 전에 말할 수 있는 것은 위 1번의 범위(그 머신, 그 빌드, 반복 실행)까지다.

**플랫폼 태그의 구성요소 [제안].** 이 표가 H1과 H7이 가리키는 유일한 목록이다. 이름은 플랫폼 태그지만 해시를 바꿀 수 있다고 본 실행 조건을 모두 담는다. 필드 이름은 C-05b와 X-02d가 정한다.

| # | 구성요소 | 식별 방법 |
|---|---|---|
| ① | OS | 종류와 커널 릴리스 |
| ② | CPU | 아키텍처와 모델 문자열 |
| ③ | 실행 환경 이미지 | 컨테이너 이미지 다이제스트. 컨테이너가 아니면 "이미지 없음"으로 적는다 |
| ④ | MuJoCo | 버전, 배포 형태(PyPI 휠, WASM 패키지, 자체 빌드), 배포 파일의 해시. 자체 빌드면 컴파일러와 빌드 플래그 |
| ⑤ | Python·NumPy | 버전 |
| ⑥ | 코어 빌드 | 코어의 커밋 식별자. 힘을 주는 경로와 그 순서가 여기에 든다 |
| ⑦ | 계산 설정 | 그 실행에 실제로 쓴 적분기, 시간 간격, 솔버 설정 |
| ⑧ | 스레드 구성 | 물리 스텝과 솔버의 스레드 수 |

**규칙**

- **H1 플랫폼 태그.** 궤적 해시와 판정은 위 표의 여덟 구성요소로 된 플랫폼 태그와 함께 기록한다. 두 태그는 여덟 구성요소가 모두 같을 때만 같은 태그다. 태그가 없는 해시는 증거가 아니다.
- **H2 재현 확인.** "재현 확인", "일치"는 태그가 같고 해시가 같을 때만 쓴다. 태그가 다르면 해시를 비교하지 않는다. 태그가 같은데 해시가 다르면 "불일치"로 기록하고 원인을 찾는다. 표에 빠진 구성요소가 있다는 뜻일 수 있다.
- **H3 기준 플랫폼.** 기준 플랫폼은 표의 ①~⑥과 ⑧을 하나로 고정한 것이다: **Linux x86-64, 다이제스트로 고정한 컨테이너 이미지, `uv.lock`으로 고정한 MuJoCo·NumPy·Python, 고정한 코어 빌드와 스레드 구성.** ⑦ 계산 설정은 실행마다 정해지므로 기준 해시마다 그 값을 태그에 함께 적는다. ② 가운데 CPU 모델은 호스팅 러너에서 고정하지 못할 수 있다. #432가 같은 이미지에서 CPU 모델이 달라도 해시가 같음을 보이면 CPU 모델은 기록만 하고 비교에서 빼도록 표를 고친다. 보이지 못하면 기준 플랫폼은 CPU 모델까지 고정할 수 있는 러너여야 한다 [확인 필요]. 저장소에 커밋하는 기준 해시와 기준 판정 수치(J-05 회귀 고정물 등), 서버 재시뮬(N-01, CB-11), 호스팅된 코어(M-08)는 이 플랫폼의 값만 쓴다. 이유: CI가 이미 Linux x86-64라서 기준 해시를 CI가 단언할 수 있고, 서버와 호스팅도 같은 플랫폼에 둘 수 있다 [추정]. 개발 머신(macOS arm64)을 기준으로 삼으면 CI가 기준 해시를 단언할 수 없다.
- **H4 다른 플랫폼의 판정.** 기준이 아닌 플랫폼(예: 창업자의 macOS arm64 로컬 코어)이 낸 판정도 판정이다. 시뮬과 몬테카를로로 냈기 때문이다(V1). 다만 태그가 기록되고, 기준 플랫폼의 값과 나란히 놓을 때는 "비교"로 표시하고 수치 차이를 적는다.
- **H5 판정 수치.** p_success가 플랫폼에 따라 얼마나 달라지는지는 재지 않았다 [확인 필요]. 접촉 뒤의 궤적 차이가 성공 경계 근처 표본의 성패를 바꿀 수 있다 [추정]. 재기 전에는 다른 플랫폼의 p_success를 같은 값이라고 말하지 않는다.
- **H6 테스트.** 같은 태그에서는 비트 일치를 단언한다. 이 단언은 "태그가 같으면 해시가 같다"는 가정에 기대고, 그 가정은 #432 전에는 검증되지 않았다. 다른 태그에서는 허용 한계로 비교하고, 그 한계는 자릿수가 달라지는 회귀를 잡는 용도이지 "플랫폼이 같은 결과를 낸다"는 보증이 아니다(지금 `spikes/mujoco-wasm`의 5e-3이 그 방식이다).
- **H7 태그가 바뀔 때.** 태그가 바뀌는 조건은 H1 하나뿐이다: 위 표의 구성요소 가운데 하나라도 값이 달라지면 다른 태그다. 여기서 따로 나열하지 않는다. 기준 플랫폼의 태그가 바뀌면 기준 해시를 다시 만들고 전후의 차이를 그 PR에 적는다. 이전 해시와의 불일치는 회귀가 아니라 태그 변경이다.
- **H8 공유 링크.** 공유 페이지는 다시 시뮬하지 않고 기록을 재생한다(F3). 번들에 판정의 태그를 싣는다. 브라우저에서 다시 돌린 결과는 "미리보기"다.

**정직한 한계**

- 지금 CI는 `ubuntu-latest`라 이미지가 고정돼 있지 않다. 워크스페이스 의존성(`pyproject.toml`, `uv.lock`)에는 아직 MuJoCo가 없고 스파이크만 스크립트 머리에서 `mujoco==4.0.0`으로 고정했다. H3은 이미지와 버전을 고정하는 작업을 요구한다.
- 같은 이미지라도 러너의 CPU가 달라지면 해시가 같은지는 재지 않았다 [확인 필요]. Linux 쪽 측정은 러너 1회이고 차이의 원인(FMA, 수학 라이브러리 등)을 조사하지 않았다. A0-05a #432가 잰다. 그 결과에 따라 위 표(특히 ② CPU 모델)와 H3이 바뀔 수 있다.
- S1에는 호스팅된 코어가 없다. 창업자가 로컬에서 만든 Halo의 판정은 macOS arm64 태그이고, 기준 플랫폼에서 다시 돌린 확인은 붙지 않는다. 그 사실을 번들의 태그로 남긴다.
- Jolt의 플랫폼 간 결정론은 재지 않았다. S4에서 서버 물리를 고를 때(N-03) 같은 규칙을 적용한다.

- 트리거 없이 열지 않는다. "더 강해 보인다"는 계획 5.2절의 평가는 측정이 아니다.

- 웹을 주 클라이언트에서 내리는 일(전환)은 이 문서의 조건으로 하지 않는다. 필요하면 `plan-change`로 창업자가 정한다.

**S4의 서버 물리.** 실시간 대결과 PvP의 서버 물리는 N-03 #264와 CB-12 #341이 그때의 측정으로 고른다. 어느 엔진이 되든 실시간 화면은 "플레이 물리"이고(계획 15.3절), 대회와 리더보드의 순위는 기준 플랫폼의 MuJoCo 코어가 다시 시뮬한 값으로 매긴다(S4 Go "서버 재시뮬 일치 100%"는 기준 플랫폼 태그가 같은 실행끼리의 일치로 읽는다 [제안]. 그 일치가 성립하는지는 #432가 먼저 검증한다). N-05 #266의 "클라이언트 선택은 engine.md를 따른다"는 그 시점의 주 클라이언트를 쓴다는 뜻이다.

## 7. 기각한 대안

| 대안 | 기각 이유 | 근거의 종류 |
|---|---|---|
| Unity | 독점 라이선스이고 엔진을 고칠 수 없다. 화면을 새로 써야 한다 | 계획 5.2절. **재지 않았다** |
| Bevy | 에디터가 없고 XR이 초기다 [추정]. 실시간 멀티를 직접 구현해야 한다 | 계획 5.2절. **재지 않았다** |
| Godot + Jolt를 S1 주 클라이언트로 | S1부터 화면이 판정 물리와 갈린다(4륜차 2개 장면에서 22.7~49.4 mm). Claude Design의 HTML을 다시 옮겨야 한다. 웹 공유가 약 39 MB이고 스레드 변형은 COOP/COEP가 필요하다. 배속의 우위는 [추정]이고 1,000개 실시간에는 Jolt도 못 닿았다 | A0-03a, A0-03b |
| Jolt를 판정 물리로 | 불변 결정 3에 어긋난다. 판정 자산(몬테카를로, 필요조건, 탐색)이 MuJoCo 위에 있다. 낙하에서 1 µm의 흔들림을 6.8 mm로 키웠고(MuJoCo는 0.001 mm), 플랫폼 간 결정론 설정이 꺼져 있을 가능성이 있다 [추정] | A0-03a, A0-03b |
| 브라우저 MuJoCo WASM을 코어로(서버 없는 제작) | 네이티브와 비트가 다르다(최대 6.144e-6 m). 바인딩이 스스로 WIP라고 적는다. 다물체와 재컴파일을 재지 않았다. 판정을 브라우저에서 내면 플랫폼 태그가 사용자마다 달라진다 | A0-01b |
| 클라이언트마다 Command 적용기와 물리를 따로 두기 | 서로 어긋난다. 경계의 D3이 막는다 | `client-adapter.md` |
| 다른 물리 엔진으로 코어 교체 | 평가하지 않았다. 판정 자산의 이식 비용이 크고 S0 측정에 그런 후보가 없다 | **재지 않았다** |

Unity와 Bevy는 S0에서 측정하지 않았다. 기각 이유는 계획의 평가이고 수치가 아니다. 6절의 조건으로 GD를 열었는데도 요구를 못 채우면 그때 다시 본다.
