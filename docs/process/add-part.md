# 새 부품 추가 절차서 (B-01d)

부품 하나를 정의 파일에서 시작해 질량·충돌 프록시·시각 glb가 나오고 테스트와 문서가 맞을 때까지 넣는 순서다. 종류별 부품(B-02 구조, B-03 구동)이 이 순서를 따른다. 근거: 이슈 #95, `docs/architecture/part-mass.md`, `collision-proxy.md`, `part-visual.md`, `docs/process/done-definition.md`. 목표는 부품 하나를 2시간 안에 넣는 것이다(`docs/plan/history/final-plan.md` Go 기준 표의 제안값이고 측정으로 확정한 값이 아니다. 실측은 아래 "소요 시간 기록").

이 문서가 정하지 않는 것: 부품 종류와 실제 사양값(B-02, B-03), 가져온 glb(L-02), 빈 곳을 깎은 메시(#496), 임의 형상 커널(#484). 정의 파일의 자리는 B-02a가 정했다: **라이브러리에 들어가는 부품은 `packages/engine/src/kinetra_engine/parts/library/<id>.json`**(파일 이름이 부품 id)이고 `PartDef.model_validate_json`으로 읽는다. 시험용 부품은 `packages/engine/tests/fixtures/parts/`에 둔다. 아래 확인 명령은 어느 경로의 파일에도 돈다.

## 0. 시작 전에 정할 것 (10분)

1. **id**: `^[a-z][a-z0-9_-]{0,63}$`. 한 번 정하면 바꾸지 않는다(프로젝트가 id로 가리킨다).
2. **파라미터**: 사용자가 바꾸는 길이만 파라미터로 둔다. 이름은 `^[a-z][a-z0-9_]{0,63}$`, 단위 m, 기본값·최솟값·최댓값을 모두 정한다.
3. **재료**: 부품은 재료를 담지 않는다. 질량은 인스턴스의 재료로 정해진다. 확인할 때는 B-07 카탈로그의 재료 하나를 고른다(`al6061-t6`, `steel-a36`, `cfrp-8552-as4-pw`, `ti-6al-4v`, `pom-delrin-150`).
4. **모든 수치의 출처**. 아래 "출처와 배지"를 먼저 읽는다. 출처가 없으면 `사용자 선언`으로 쓰고 그렇다고 적는다. 값을 지어내서 `인용`으로 쓰지 않는다.

## 1. 정의 파일 쓰기 (`PartDef` JSON)

필드는 `packages/core/src/kinetra_core/partdef.py`(`PartDef`, `ParamDef`, `SnapPoint`, `SpecDef`)와 `shape.py`(`Shape`, 기본형)다. 예는 `schemas/examples/PartDef.block-with-hole.json`과 이 절차서의 시험 부품 `packages/engine/tests/fixtures/parts/trial-bracket.json`이다. JSON을 손으로 쓰기보다 파이썬으로 만들어 `PartDef.model_validate`를 통과시킨 뒤 `model_dump(mode="json", exclude_none=True)`로 쓰는 편이 틀리기 어렵다. 위치와 치수에 계산한 수를 넣을 때는 `repr(float)`을 그대로 쓴다(아래 "맞닿은 요소").

### 출처와 배지

- 모든 수치(`Quantity`)는 배지와 출처가 있어야 한다. 없으면 모델이 거절한다. 형상 레시피 전체와 스냅 포인트 하나는 각각 배지 하나와 출처 하나를 가진다.
- `인용`(`cite`): 데이터시트·표준의 값을 옮긴 것. `source.locator`나 `url`이 필요하고 가능하면 `license`(SPDX)를 쓴다.
- `사용자 선언`(`declared`): 우리가 정한 값. `declared_by`와 `declared_at`을 쓸 수 있다. 시험 부품은 전부 이것이다.
- `기본값`(`default`), `추정`(`estimate`): 근거가 약한 값. 출처 문구에 방법과 입력을 쓴다.
- `시뮬`(`sim`)은 계산 결과의 배지다. 정의 파일에 쓰지 않는다.
- 약한 배지의 값으로 부품 사양을 "인용"처럼 보이게 하지 않는다(핵심 가치 V5).

### 형상 레시피

- 요소는 기본형 `box`(`size_x/y/z` 전체 길이), `cylinder`(`radius`, `length`, 축은 로컬 z), `sphere`(`radius`)이고 `operation`은 `add`(재료) 또는 `subtract`(빈 곳)다. 위치는 요소의 중심, 단위 m, 부품 로컬 좌표(오른손, +Z 위)다.
- 모든 치수와 위치는 `offset + Σ factor × 길이 파라미터`다. 파라미터의 **전 범위에서** 치수가 0보다 커야 한다(`PartDef`가 확인한다).
- **요소는 겹치지 않는 합**이다(`part-mass.md`). 더한 요소끼리 내부가 겹치면 안 되고, 뺀 요소는 더한 요소 하나 안에 완전히 들어 있어야 한다. 어기면 `ShapeError`로 거절된다. 겹치는 부품은 요소를 겹치지 않게 나눈다(L자는 상자 둘로).
- 구멍(`subtract`)이 있는 부품은 시각 메시에서 **파이지 않고**, 충돌 프록시에서는 **관통 보어(판의 구멍, 관)면 상자 조각으로 분해돼 비워지며**(`decomposed_voids`, 호스트별 부호 있는 오차, 허용 오차 기본 0.10, B-01f) 그 밖의 빈 곳(막힌 포켓, 구, 비스듬한 구멍)은 **메워진다**(`filled_voids`, 이유는 `derivation.assumptions`). 이 근사는 지워지지 않고 결과에 나온다(`volume_error`, 글의 `extras.kinetra.voids`). 정의 파일에서 할 일은 없고 PR 본문에 이 부품이 구멍을 가진다고 적는다.
- 모깎기·모따기·나사산은 표현하지 못한다(`part-mass.md` "못 하는 것").

### 맞닿은 요소: 돌린 요소를 반올림해 붙이지 않는다

겹침 검사의 공차는 비교하는 두 요소의 큰 쪽 크기의 상대 1e-9(0.2 m 상자면 2e-10 m)다. 면이 맞닿는 요소는 겹침이 아니지만 **돌린 요소를 맞닿게 놓으려고 중심 좌표를 7자리쯤으로 적으면 반올림 방향에 따라 겹침으로 거절된다.** 0.2 m 정육면체 두 개, 둘째를 z축으로 45° 돌려 x로 놓은 경우 맞닿는 거리는 $0.1 + 0.1(\cos 45^\circ + \sin 45^\circ) = 0.24142135623730954$이고 `0.2414214`는 통과, `0.2414213`은 거절이다(`test_add_part_the_seven_digit_example_of_part_mass_md`).

측정한 규칙(각 20.5°, 30°, 45°, 60°에서 소수 3~12자리까지 올림과 내림을 모두 시험했다, `test_add_part_rounding_away_from_a_rotated_neighbour_is_always_accepted`):

| 쓰는 법 | 결과 |
|---|---|
| 이웃에서 **멀어지는 쪽으로 올림**(틈이 생긴다) | 3~12자리 모두 통과. 틈은 실제 틈이다(올림은 마지막 자리 하나만큼까지 벌린다: 7자리면 최대 1e-7 m, 3자리면 최대 1e-3 m) |
| **내림**(파고든다) | 4개 각도 모두 7·8자리에서 거절. 4개 각도 모두 11자리부터 통과. 파고든 깊이가 위 공차 아래일 때만 통과 |
| 계산한 값을 `repr(float)`로 전부 | 통과 |

그러니: (1) 가능하면 돌린 요소를 맞닿게 놓지 않고 축에 나란한 요소끼리 맞닿게 쪼갠다. (2) 돌린 요소를 붙여야 하면 위치를 파이썬으로 계산해 `repr(float)`을 쓰거나, 멀어지는 쪽으로 올리고 그 틈을 PR 본문에 적는다. (3) 내림한 값을 쓰지 않는다. 거절 메시지(`... overlap`)가 나오면 먼저 이 반올림을 의심한다.

### 스냅 포인트

`id`, `kind`, `accepts`(호환 태그, B-04b가 맞춘다), `position`(m, 파라미터를 따를 수 있다), `orientation`(쿼터니언 `{x,y,z,w}`, 단위 노름), 배지와 출처. 위치가 가리키는 파라미터는 길이(m)여야 한다. 스냅 포인트 id는 파라미터 이름과 같을 수 없다.

## 2. 확인 (2분)

```
uv run python -m kinetra_engine.parts PATH/part.json --material al6061-t6 --out /tmp/part-check
```

정의를 읽고, 기본 파라미터로 질량·충돌 프록시·glb를 만들고, JSON 보고서 하나를 낸다: 질량, 무게중심, 관성, 프록시 부피 오차, 메워진 빈 곳, 안 그려진 빈 곳, glb 바이트, 단계별 밀리초. 정의가 거절되면 사유와 함께 종료 코드 1이다. `--out`은 `<id>.glb`를 쓴다.

보고서의 부피(또는 질량)와 무게중심의 **세 성분 모두**를 손으로 계산한 값과 맞춰 본다. 보고서가 낸 값은 맞는지 알려 주지 않는다. 한 성분만 보면 틀린 부품이 맞아 보일 수 있다(아래 소요 시간 기록의 `trial-spacer`: 높이 오프셋 오타로 질량이 2배였는데 무게중심 z는 우연히 손계산과 같았다). 파라미터의 최솟값과 최댓값에서도 확인한다(`mass_properties(part, material, {"width": Quantity(...)})`).

## 3. 테스트 (30분)

새 파일 `packages/engine/tests/test_<id>.py`에 아래를 둔다. 기대값은 코드를 읽어 쓰지 말고 교과서 식으로 손계산해 적는다(`test_add_part.py`가 예다).

1. 기본 파라미터의 질량·무게중심이 손계산과 1e-9 상대 오차 안에서 같다.
2. 파라미터를 바꾸면 질량이 식대로 바뀐다(최솟값, 최댓값). **치수 변경이 질량에 반영된다**(B-02a의 DoD).
3. 범위 밖 파라미터, 알 수 없는 파라미터는 `ShapeError`다.
4. 스냅 포인트의 위치가 파라미터를 따르는 경우 값이 식대로 나온다.
5. 구멍이 있으면 `filled_voids` 또는 `decomposed_voids`와 `volume_error`가 손계산과 같다(메우면 메운 부피, 분해하면 호스트의 부호 있는 오차가 허용 오차 안).
6. glb가 `tests/gltf_validate.py`의 `validate()`를 통과한다. 고정 파일을 새로 두려면 `tests/gltf_samples.py`의 `SAMPLES`에 더하고 `uv run python packages/engine/tests/gltf_samples.py`로 다시 쓴다(`tools/gltf-check`가 CI에서 공식 검증기로 본다).
7. 사양(`specs`)이 있으면 배지가 의도와 같다(`인용`이면 위치가 있다).

실행: `uv run pytest packages/engine -q -k <id>`.

## 4. 캐시는 따로 할 일이 없다

컴파일 결과는 `kinetra_engine.parts.PartCache`가 정의·재료·파라미터 값(·glb는 외형)의 해시로 기억한다. 부품을 넣을 때 할 일은 없고 알아 둘 것만 있다.

- 키는 정의의 값 전체다. 숫자, 배지, 출처 문구, 요소와 파라미터의 **순서**가 하나라도 다르면 다른 항목이다. 정의를 고치면 새 항목이 생기고 옛 결과가 나가는 일은 없다(`test_cache_definition_hash_changes_with_every_leaf_of_the_definition`).
- 충돌 프록시는 재료를 읽지 않아 재료와 무관하게 한 항목이다.
- 정의를 제자리에서 고치지 않는다(모델은 불변이다). 고친 정의는 새 `PartDef`로 만든다.
- 자세한 규칙과 한계: `docs/architecture/part-cache.md`. `uv run pytest packages/engine -q -k cache`.

## 5. 마감 기준 (라이브러리에 들어가는 부품)

B-02의 범위 밖 문구가 "상자·원통 그대로의 외형. 마감 기준은 부품 추가 절차서를 따른다"이다. 원본 계획의 원칙은 "양보다 질. 원통·상자 외형은 MVP 합격 기준에서 탈락 사유"다(`docs/plan/history/final-plan.md` 6절). 이 절차서는 다음을 요구한다.

1. 시각 glb를 그린 화면 캡처가 PR에 있다: `pnpm --filter @kinetra/gltf-check capture`(무거운 실행이다. `docs/process/dev-resources.md`의 가드를 통과해야 하고 CI의 `screenshots` 워크플로가 PR마다 돌려 올린다). 로컬에서 못 돌리면 CI 아티팩트 링크를 쓴다.
2. 그 캡처가 **한 개의 상자나 원기둥이 아니라 부품의 모습으로 읽힌다**: 요소를 나누어 윤곽을 만든다(휠은 림과 타이어, 브래킷은 판과 세움). 이것은 사람이 PR에서 판단한다. 판단을 숫자로 바꾸지 않았다(기준값은 정하지 않았다).
3. 레시피가 표현하지 못해 그림이 다른 곳(구멍, 모깎기)은 PR 본문에 적는다. 숨기지 않는다.

기본형의 합으로 윤곽이 나오지 않는 부품은 이 컴파일러로는 마감되지 않는다. 그 부품은 #484(커널)나 L-02(가져온 glb)를 기다리고, 상자·원통 그대로의 외형으로 라이브러리에 넣지 않는다.
