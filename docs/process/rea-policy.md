# REA 허용·금지 수칙 (A0-06a)

REA(`morluto/rea`, MIT)는 코딩 에이전트가 네이티브 바이너리, JS/Electron 앱, .NET 어셈블리, 웹사이트, 런타임 동작을 들여다보게 하는 MCP + CLI다. 근거는 `docs/plan/studio-plan.md` 6절이고, 이 문서가 그 표를 에이전트와 사람이 따를 수칙으로 풀어 쓴 것이다. 이 문서는 법률 자문이 아니다. 상표·특허와 표현의 경계는 [확인 필요]다.

## 한 줄 요약

우리 빌드와 허용적 라이선스 오픈소스는 REA로 연구해도 된다. 허용 목록에 등록된 조건부 대상(GPL·LGPL, 공개 웹)은 표에 적은 관찰 범위 안에서만 한다. 독점 게임은 어떤 경우에도 열지 않는다. 독점 제품은 클린룸 방식으로 밖에서만 본다.

**기본은 금지다.** `tools/rea/allowlist.txt`에 없는 대상에는 REA를 쓰지 않는다. 확신이 없으면 대상이 아니다.

## 왜 (대목표와 핵심 가치)

- 대목표 G1: 창업자가 세 행성 어디서든 상상한 물건을 만들어 정직한 판정이 붙은 Halo로 내보낸다.
- 핵심 가치 V5 깨끗한 출처: 수치, 부품, 에셋은 출처와 라이선스가 기록된 것만 쓴다. 독점 게임을 풀어 얻은 코드·부품 데이터·에셋은 출처를 기록할 수도, 라이선스를 받을 수도 없다. 리뷰 루브릭 1번이 "독점 제품에서 나온 코드·에셋"을 금지 사항으로 못박는다(`docs/process/review-rubric.md`).
- REA는 .NET을 쉽게 풀어 준다는 점이 곧 위험이다. KSP와 Space Engineers가 정확히 그런 대상이다. 그래서 무엇을 열어도 되는지를 먼저 적는다.

## 금지 행위

독점 게임·독점 소프트웨어에 대해 REA 또는 다른 어떤 수단으로도 다음을 하지 않는다.

1. **디컴파일·역어셈블.** .NET 어셈블리, 네이티브 바이너리, 번들 스크립트를 풀어 코드를 읽는 일.
2. **에셋 추출.** 모델, 텍스처, 소리, UI, 파츠 정의 파일을 꺼내는 일.
3. **데이터 복제.** 부품 수치, 행성 상수, 밸런스 표, 파일 형식 명세를 풀어서 또는 측정 자동화로 대량 수집해 베끼는 일.
4. **DRM·라이선스 우회.** 크랙, 훔친 키, 활성화 우회, 약관이 막는 자동화.
5. **참고하며 쓰기.** 풀어 본 코드를 곁에 두고 우리 코드를 쓰는 일. 이미 풀어 봤다면 그 사람은 그 부분의 구현자가 될 수 없다는 규칙은 [제안]이며, 창업자가 이 PR(허용 목록 수칙 승인 경로)에서 승인하기 전에는 구속력이 없다. 승인 전에도 "독점 바이너리는 열지 않는다"(아래 6번)가 이를 대신한다.
6. **독점 바이너리 열기.** 1~2인 팀은 관찰자와 구현자를 나눌 수 없으므로 "독점 바이너리는 열지 않는다"로 더 엄격하게 잡는다(계획 6절).

REA는 제3자 상용 도구(Hopper, IDA 등)와 연결할 수 있다. 그 도구는 합법적으로 얻고 사용 권한이 있는 것만 쓴다. REA의 MIT 라이선스는 그 도구의 라이선스를 대신하지 않는다(REA README의 "License", "Disclaimer" 절이 같은 취지로, 합법적으로 얻고 사용 권한이 있는 도구와 소유했거나 검사할 권한이 있는 소프트웨어의 분석을 말한다. 2026-11-10에 https://github.com/morluto/rea 에서 확인).

## 독점 제품은 이렇게 본다 (클린룸)

1. 직접 플레이하고, 공개 문서와 개발자 발표를 읽는다.
2. 관찰한 동작을 `docs/research/benchmarks/<제품>.md`에 **우리 말로** 적는다. 양식은 `docs/research/benchmarks/_template.md`다. 원문을 길게 붙이거나 스크린샷·영상 프레임·에셋을 저장소에 넣지 않는다.
3. 구현은 그 문서만 보고 한다. 구현 PR 본문에 어느 관찰 기록을 근거로 했는지 링크한다.
4. 관찰 기록의 수치는 값 배지를 붙인다. 공개 문서에서 가져온 값은 `인용`(출처 URL), 우리가 플레이하며 잰 값은 `추정`이다. 근거 없는 값은 쓰지 않는다.
5. 아이디어와 동작은 배우되 표현은 베끼지 않는다. 이름·로고·UI 문구·아이콘·고유 용어는 따라 쓰지 않는다. 상표·특허와의 경계는 [확인 필요]다.

## 에이전트가 REA를 쓰기 전에

REA는 개발 보조 도구다. 제품 런타임이나 사용자 경로(에이전트 작업대)에 넣지 않는다.

1. 대상이 `tools/rea/allowlist.txt`에 있는지 본다. 없으면 REA를 쓰지 않고 멈춘다.
2. 구분이 `조건부`이면 그 줄의 조건을 PR 본문에 옮겨 적고 지킨다.
3. 결과는 `docs/research/rea/<주제>.md` 또는 관찰 기록으로 남긴다. 우리 빌드 점검은 A0-06b가 `docs/research/rea/own-build.md`에 남긴다.
4. REA는 공식 출처에서만 받는다: [morluto/rea](https://github.com/morluto/rea), [rea.tools](https://rea.tools/), npm `rea-agents`. 이름이 비슷한 저장소나 복사본은 쓰지 않는다. 새 의존성이 되는 경우 원장(`assets/LEDGER.csv`)에 행을 더한다.

## 허용 목록 변경 절차

- 목록 변경은 **창업자 승인 대상**이다(`docs/process/review-rubric.md` "창업자 승인 대상"). PR 하나가 한 대상만 더하거나 뺀다.
- 변경 PR 본문에 대상의 라이선스(SPDX)·확인 URL·확인 날짜와 구분(허용/조건부)을 적는다. 금지 대상은 목록에 추가할 수 없다. 이 문서의 금지 행위를 바꾸려면 `type:plan-change` 이슈가 필요하다.
- 대상을 뺄 때(라이선스가 바뀌었거나 의심이 생겼을 때)는 승인 없이 먼저 빼고 사후에 보고한다. 보수적인 방향이기 때문이다 [제안].

## 금지 대상을 실수로 열었다면

1. 즉시 멈추고 REA 출력과 메모를 저장소에 올리지 않는다.
2. 그 제품의 해당 부분 구현을 보류하고 창업자에게 알린다. 구현자를 바꾸는 방안은 위 5번의 [제안]이 승인되면 그때 더한다(승인 전에는 구속력이 없다).
3. 일어난 일을 새 이슈로 적는다 [제안].

## 목록 파일 형식 (`tools/rea/allowlist.txt`)

형식 검사 스크립트는 두지 않는다(이슈 DoD 밖). 리뷰어가 아래 형식을 눈으로 본다. 구분과 종류의 짝은 `own-build`·`oss-permissive`는 `allow`, `oss-copyleft`·`public-web`은 `conditional`이다. UTF-8, 한 줄에 대상 하나. `#`으로 시작하는 줄과 빈 줄은 주석이다. 필드는 탭이 아니라 ` | `(공백, 세로선, 공백)로 나눈다.

```
<구분> | <종류> | <대상> | <라이선스 또는 약관> | <확인 URL> | <확인 날짜> | <조건·메모>
```

| 필드 | 값 |
|---|---|
| 구분 | `allow` 또는 `conditional` (금지 대상은 적지 않는다. 목록에 없으면 금지다). `own-build`·`oss-permissive`는 `allow`, `oss-copyleft`·`public-web`은 `conditional`만 쓴다 |
| 종류 | `own-build`, `oss-permissive`, `oss-copyleft`, `public-web` |
| 대상 | 저장소 경로, 저장소 URL, 또는 서비스 URL |
| 라이선스 | SPDX 식별자, 우리 빌드는 `own`, 약관을 따르는 공개 웹은 `terms` |
| 확인 날짜 | `YYYY-MM-DD` |
