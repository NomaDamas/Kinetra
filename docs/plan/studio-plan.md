## 1. 한 줄 정의, 북극성, 핵심 가치

**정의:** 빈 행성 평지의 작업대에서 에이전트와 함께 무엇이든 조립하고, 그 행성의 물리로 돌려 보고, 가정과 확률이 붙은 Halo(영상 + 플레이 링크)로 내보내는 스튜디오.

**북극성:** 누구든 상상한 물건을 직접 만들어 물리 세계에서 돌려 보고, 정직한 판정과 함께 남에게 보여 준다. 경로는 **생각 → 상상 → 실제 물리 세계**다.

핵심 가치의 원문은 아래 다섯 줄이다. 이슈와 PR은 이 문장을 그대로 인용한다(`docs/plan/values.md`).

- **V1 정직한 판정** — 판정은 시뮬과 몬테카를로만 한다. 확률, 가정, 한계를 숨기지 않는다. 1회 미리보기 실행을 판정이라 부르지 않는다.
- **V2 상상에서 현실까지** — 모든 기능은 생각 → 상상 → 실제 물리 세계의 거리를 줄여야 한다.
- **V3 한 번에 100%** — 작은 단위를 증거와 함께 완전히 끝낸다. 부분 완성은 미완성이다.
- **V4 보여줄 수 있는 결과** — 결과는 시뮬 리플레이 그대로 영상과 플레이 링크가 된다. 연출은 카메라·조명·편집만 바꾸고 궤적은 바꾸지 않는다.
- **V5 깨끗한 출처** — 수치, 부품, 에셋은 출처와 라이선스가 기록된 것만 쓴다. 사용자가 선언한 값과 가져온 에셋은 배지로 구분한다.

판단: V2·V3는 그대로다. V1은 마지막 문장을, V5는 둘째 문장을 보강했고, V4는 연출의 허용 범위를 명시했다. 가치는 늘리지 않는다. "에이전트는 제안하고 사람이 수락한다"는 가치가 아니라 제품 규칙(4.4)이다.

## 3. 제품 정의: Kinetra Studio

Halo Studio가 곧 제품이다. Halo는 그 산출물 한 편을 가리킨다.

| 요소 | 정의 |
|---|---|
| 작업대 | 평지 위 조립 공간. 조립 중에는 물리를 끄고, 실행할 때 모델을 컴파일한다 |
| 행성 | 지구·화성·달의 **허허벌판**. 행성이 정하는 것은 중력, 대기 밀도, 지면 마찰 분포, 하늘·조명뿐이다. 값은 출처가 붙은 데이터 파일에 둔다. 구형 행성, 궤도, DEM 지형은 없다 |
| 라이브러리 | ① 기본 부품(파라메트릭, 사양 출처 있음) ② 내 것(저장한 조립체, 가져온 glb) ③ 생성(생성 3D는 시각 스킨 전용, S2) |
| 에이전트 | 텍스트·음성 의도를 편집 명령 묶음으로 바꿔 제안한다. 사람이 미리 보고 수락한다 |
| 물리 설정 | 강체 질량·무게중심·관성, 관절과 한계, 액추에이터, 재질, 파단 임계, 제어 스케줄(추력기 분사, 구동, 분리) |
| 실행 모드 | 시뮬(S1) → 미션(S2) → 게임(S2) → 대결(S2, 실시간은 S4). 같은 프로젝트에 목표·예산·점수 규칙을 얹어 가는 구조다 |
| Halo 출력 | 리플레이 영상(mp4) + 같은 프로젝트가 열리는 공유 플레이 링크. 판정 자막이 자동으로 붙는다 |
| 수역(S2) | 평지 위에 놓는 물 영역. 부력·수중 항력·부가질량은 근사이고 라벨이 붙는다. 파도는 시각 전용이다. 화성·달의 액체는 `사용자 선언`이다(15.2절) |
| 대결(S2) | 두 진영의 설계가 투사체·충돌·파단으로 겨루는 게임 모드. 결과는 "게임 물리"이고 안전선(15.3절) 안에서만 다룬다 |
| 하드웨어 사양(S2) | BOM, STEP·STL, 수계산 라벨, 질량 폐루프 재판정을 묶은 사양서. 실물 검증은 여전히 0건이고 키트는 S5다(15.4절) |

**인터뷰는 선택 기능이다.** Halo를 만들 때 에이전트가 의도(무엇을 보여 줄지, 성공 조건)를 몇 문항으로 묻는 단계이고 건너뛸 수 있다. 이 해석은 [추정]이며 창업자 확인이 필요하다.

## 4. UX/UI 설계

### 4.1 화면 구조

```
┌─────────────────────────────────────────────────────────────────────────┐
│ 프로젝트명 │ 행성 [지구|화성|달] │ [조립|실행|판정|Halo] │ 증거 배지 │ 공유 │
├───────────┬─────────────────────────────────────────┬───────────────────┤
│ 라이브러리 │                                         │ 인스펙터          │
│  기본 부품 │        3D 뷰포트 (작업대 / 평지)        │  강체: 질량·COM   │
│  내 것     │   기즈모 · 스냅 · 고스트(변경안)        │  관절 · 한계·파단 │
│  가져오기  │   질량중심 · 지지 다각형 오버레이       │  액추에이터·제어  │
│  (생성)    │                                         │  재질 · 값 배지   │
├───────────┴─────────────────────────────────────────┴───────────────────┤
│ 에이전트 바: [🎤] 입력 ▸ 변경안 카드 [미리보기][수락][부분][거절]        │
│ 타임라인: ▶ ⏸ ↺ │ 실패 표식 ▲ 파단 ✕ │ 판정 카드 열기                    │
└─────────────────────────────────────────────────────────────────────────┘
```

모드는 네 개다. **조립**(물리 꺼짐), **실행**(미리보기 1회, 수동 조종), **판정**(탐색 + 몬테카를로), **Halo**(카메라·자막·내보내기). 뷰포트가 항상 중심이고 패널은 접을 수 있다.

조립 모드의 L0 표시(PC-02): 질량중심과 지지 다각형에 더해 **추력중심·추력선**(제어 스케줄의 시점별, B-13)과 **지구·화성·달 세 값의 추력 대 중량비**(B-14)를 보여 주고, 실행 전 점검은 한 목록(X-11)으로 낸다. 모두 해석 계산이고 판정이 아니다.

### 4.2 핵심 플로우

**A. 로켓 자동차 공중제비 Halo (텍스트·음성 중심)**
1. 새 프로젝트 → 지구 평지.
2. "1.3톤 차체에 냉가스 추력기를 달아 점프대에서 한 바퀴 돌고 바로 착지하게 해 줘."
3. 에이전트가 변경안 카드 넷을 낸다: 차체와 바퀴 / 추력기 배치 / 점프대 소품 / 성공 조건(회전각, 착지 자세·속도). 카드마다 고스트와 질량·무게중심 변화가 보인다. kN급 추력기는 카탈로그에 없으므로(최대 8.9 N) "카탈로그 밖 · 사용자 선언" 배지가 붙는다.
4. 사용자가 3D에서 추력기를 기즈모로 옮기고 인스펙터에서 추력을 고친다.
5. 실행 → 회전 부족으로 실패 → 타임라인 표식.
6. 탐색(CMA-ES가 분사 스케줄을 찾는다) → 성공 사례 발견 또는 `NOT_FOUND_IN_BUDGET`(약한 증거).
7. 판정 → p_success와 신뢰구간, 판정을 뒤집는 가정 1위.
8. 달·화성으로 전환해 다시 판정하고 비교한다.
9. Halo → 카메라 선택 → 자막 자동 → mp4 + 링크.

기존 측정값은 그대로 영상에 들어간다: 노즐당 8 kN에서 15.2% [12.3, 18.6], 추력 잡음 ±10%에서 0.8%. 차체는 자체 제작이고 상표는 쓰지 않는다.

**B. 화성 로버 (마우스 중심)**
1. 화성 평지에 경사로 소품을 놓는다.
2. 라이브러리에서 빔·휠·모터를 끌어 놓는다. 스냅 포인트가 맞으면 붙고 틀리면 거부된다.
3. 인스펙터에서 재질을 바꾸면 질량과 무게중심이 바로 갱신된다.
4. 정역학 검사가 "이 경사에서 전복"을 실행 전에 경고한다. 실행 모드에서 키보드로 몰아 본다.
5. 판정: 지면 마찰을 분포로 흔든 등판 성공 확률. 같은 로버를 지구·달에서 나란히 돌린다.

**C. 만화 장면 검증 (에이전트 대화 중심)**
1. "사람이 자동차를 30 m 던질 수 있어?"
2. 에이전트가 장면을 질량·속도·높이·시간으로 옮기며 빠진 값을 묻는다(선택 인터뷰).
3. 필요조건 스크린이 필요 에너지·출력을 계산해 `INFEASIBLE_NECESSARY_CONDITION` 카드를 낸다. 비교 기준(사람 근육 출력)은 출처가 있어야 하고 없으면 [확인 필요]로 표시한다.
4. 강체로 되는 부분(투사체, 충돌)만 시뮬한다. 기·빔·변신은 "모델 밖"으로 분류한다.
5. 원작 캐릭터 외형은 쓰지 않는다. S1에는 필요조건 카드와 투사체 시뮬만 넣고 장면 유형 확장은 S3이다.

### 4.3 입력 모드

모든 입력은 같은 **편집 명령(Command)**으로 바뀐다. 되돌리기, 고스트 미리보기, 리플레이가 입력 수단과 무관하게 동작하는 이유다.

| 모드 | 맡는 일 | S1 범위 | 한계 |
|---|---|---|---|
| 텍스트 | 의도, 수치, 일괄 변경 | 완성 | 공간 위치 지정이 모호하다 |
| 음성 | 손이 바쁠 때의 텍스트 대체. 헤드셋 안에서는 주 입력 | 받아쓰기 → 인식문 확인 → 텍스트와 같은 경로 | 한국어 인식 품질 [확인 필요]. 삭제류 명령은 확인 단계를 둔다 |
| 마우스·키보드 | 정밀 배치, 기즈모, 스냅(위치·각도), 대칭 복제(평면·방사), 수치 입력 | 완성 | — |
| XR(WebXR 헤드셋) | 잡기, 놓기, 돌리기, 스냅 결합, 크기 가늠 | **완성**(창업자 확정) | 정밀 수치가 안 된다. 스냅과 음성으로 보완한다. 시험용 헤드셋 확보는 [확인 필요] |

**헤드셋 안에서의 조립.** 손 추적이나 컨트롤러로 부품을 잡아 옮기고 돌린다. 가까운 호환 스냅 포인트에 고스트가 뜨고 놓으면 붙는다. 손목 팔레트에서 새 부품을 꺼내고, 누르고 말하기로 에이전트에게 요청하면 변경안의 고스트와 카드가 공간에 뜬다. 잡고 있는 부품이 "이것"의 문맥이 된다. 작업대는 탁상 크기와 실물 크기를 오간다(보기만 바뀌고 치수는 그대로다). 증거 단계 배지와 "1회 실행" 표시는 공간에도 있다. 개발과 CI는 WebXR 에뮬레이터로 하고, 실기 시험은 창업자 작업(F)이다. 웹캠 손 추적(MediaPipe)은 S2로 미뤘다.

### 4.4 에이전트와의 협업

- **제안 → 미리보기 → 수락.** 변경안은 명령 묶음이다. 3D에는 반투명 고스트, 카드에는 수치 변화(질량, 무게중심, 부품 수)가 뜬다. 수락, 부분 수락, 거절, 되돌리기가 된다.
- **3D에서 직접 수정.** 사용자가 고른 부품이 에이전트의 문맥이 된다("이것만 더 가볍게").
- **검증기.** 겹침, 공중에 뜬 부품, 무효 스냅, 스키마 위반은 화면에 오기 전에 거부되고 에이전트가 정해진 횟수 안에서 다시 시도한다.

| 에이전트가 한다 | 하지 않는다 |
|---|---|
| 부품 추가·배치·결합, 파라미터·재질 변경 | 판정 선언 |
| 제어 스케줄 초안, 탐색·판정 실행 요청 | 행성 상수·물성 DB 변경 |
| 롤아웃 수치만 인용한 실패 설명 | 카탈로그에 없는 사양을 있는 것처럼 쓰기 |
| 가져온 에셋의 프록시·질량 제안(추정 배지) | 물리 부품의 형상을 생성 메시로 만들기 |

**인스펙터 항목:** 강체(질량, 무게중심, 관성; 계산값인지 선언값인지), 관절(종류, 축, 한계, 파단 임계), 액추에이터(토크-속도 곡선 또는 추력 곡선, 추진제 질량), 재질(밀도, 항복강도, 마찰), 제어 스케줄. 모든 수치 옆에 배지가 붙는다: `시뮬` `인용` `기본값` `사용자 선언` `추정`.

### 4.5 물리 판정 표시

증거는 네 단계이고 상단 배지가 현재 단계를 보여 준다.

| 단계 | 화면 문구 | 근거 |
|---|---|---|
| L0 조립 | 질량, 무게중심, 정역학 경고, 추력중심·추력선, 행성별 추력 대 중량비와 연소 시간 | 해석 계산 |
| L1 미리보기 | "1회 실행. 판정이 아닙니다" | 명목 모델 1회 |
| L2 판정 | `FEASIBLE_FOUND` + p_success·95% CI / `INFEASIBLE_NECESSARY_CONDITION` / `NOT_FOUND_IN_BUDGET`(약함) / 모델 밖 | 탐색 + 몬테카를로 |
| L3 실측 | "실물 검증 없음" | 현재 0건이다. 숨기지 않는다 |

판정 카드에는 가정표(값, 분포, 출처, 신뢰도), 민감도(어느 가정이 판정을 뒤집는가), "이 모델이 보지 않는 것"(CFD, 연소, FEM, 열)이 함께 붙는다. 가정표에는 모델 라벨이 들어간다: "근사: 집중 항력"(W-03b)과 "근사: 균일 중력(행성별 g 하나)"(W-06, PC-02). 색은 성공·실패가 아니라 증거의 강도를 나타낸다. 이 원칙은 과거 판정이 가정에 따라 13%↔77%로 흔들린 데서 나왔다.

### 4.6 행성 전환, 실패 리포트, Halo

- **행성 전환:** 상단 한 번. 설계는 두고 상수만 바꿔 다시 컴파일한다. 이전 판정은 무효로 표시된다. 비교 보기는 세 행성을 나란히 재생한다.
- **실패·파단:** 파단은 FEM이 아니라 결합부 임계값(물성 × 단면, "단순화 모델" 표시)이다. 리포트에는 원인(전복, 슬립, 토크 부족, 추진제 고갈, 파단), 타임라인 시점, 임계 대비 여유가 나온다. 원인은 시스템이 궤적에서 분류하고(J-06) 어느 묶음에도 들지 않으면 "분류되지 않음"이라고 쓴다. 분류는 성공 조건이 실패한 실행에만 하고, 원인은 실패 시점 또는 그 이전의 사건에서만 뽑는다. 성공한 실행의 실패 원인은 0건이다. 공중 구간, 스케줄대로 끝난 연소, 의도한 분리 같은 정상 상태 변화는 사건으로만 남는다. 결합 해제 이벤트는 사유로 가른다: "임계 초과"만 파단이고 "의도한 분리"는 실패 원인이 아니다. 원인은 "성공 조건이 실패하기 전에 임계를 넘은 사건"이며 인과를 증명한 것이 아니다. 파단은 시간 간격을 1/2, 1/4로 바꿔도 같은 결합이 풀려야 하고, 못 지키는 조건에서는 "시간 간격 민감: 약한 증거"가 붙는다(X-10). 풀려 나간 조각은 지우지 않고 같은 월드에서 끝까지 시뮬해 리플레이에 남기며, 접촉 물리와 성공 조건 평가의 대상으로 남는다(X-13).
- **분리(PC-02):** 분리기는 명령을 받으면 결합을 푸는 부품이고, 분리는 제어 스케줄의 한 항목이다(순서 목록을 따로 두지 않는다). 에너지원은 "선언 분리 충격량" 수치 하나뿐이며 화약·점화의 모델과 필드는 없다. 의도한 분리는 타임라인에서 파단과 다른 표식으로 남는다(B-15, X-08, X-09).
- **재생 속도(PC-02):** 타임라인의 느리게·빠르게는 기록된 궤적을 보는 속도다. 물리 시간 간격과 궤적 해시를 바꾸지 않으며, 정확도를 바꾸는 물리 시간 가속은 두지 않는다(X-12).
- **Halo 영상:** 질문 → 시도 → 판정 공개 → 엔드카드. p_success, CI, 핵심 가정이 자막으로 들어간다. 판정 없이 내보내면 "판정 없음: 1회 실행"이 남는다. 성공 장면이 표본 중 하나라는 것도 표시한다. "시도" 구간에는 실패한 시도를 넣을 수 있고, 빼면 엔드카드에 시도 횟수가 남는다(H-06).

## 5. 기술 아키텍처 결정

### 5.1 원칙: 최종 버전을 막지 않는 구조

창업자의 기준은 "최종 버전에 도달할 수 있는 선택"이다. 최종 버전은 열린 세계, 멀티와 파괴, XR, 공유 링크, 실시간 플레이를 모두 요구한다. 어떤 단일 클라이언트도 이 전부에서 가장 낫지 않으므로, 엔진을 하나 고르는 대신 **갈아 끼울 수 있는 경계**를 먼저 고정한다.

```
클라이언트(갈아 끼움)              코어(고정, 엔진 독립)
 웹: three.js/R3F + WebXR  ─┐      Project JSON(원본)
 Godot + Jolt (S2+, 조건부) ─┼─ 어댑터 ─ 명령 계층(Command) + 검증기 ─ MCP 서버
 헤드리스 참조 클라이언트   ─┘  경계     컴파일·실행·판정 서비스: MuJoCo 네이티브(권위)
```

- **코어가 쥐는 것:** 프로젝트, 명령의 검증과 적용, 컴파일, 실행, 판정. 판정은 어떤 클라이언트에서도 코어의 MuJoCo 네이티브만 낸다.
- **클라이언트가 쥐는 것:** 렌더, 입력 → Command, 실행 스트림 재생. 실시간 플레이를 위해 클라이언트가 자체 물리(Jolt)를 돌릴 수 있지만, 그 결과는 "플레이 물리"로 표시하고 판정이라 부르지 않는다.
- **어댑터 경계의 계약 다섯 가지:** 문서 구독, 명령 발행, 실행 스트림 프레임, 에셋 로딩, 입력 매핑. 헤드리스 참조 클라이언트와 MCP 서버가 S1에서 이 경계를 실제로 쓰므로, 경계가 웹에 묶였는지는 S1 안에서 드러난다(C-05).

정직한 비용: 경계를 두면 S1이 느려진다(프로토콜, 적합성 테스트). 그리고 플레이 물리와 판정 물리가 갈리는 순간 V1을 지키는 일이 표시 문구와 일치 시험에 달리게 된다.

| XR | 에뮬레이터와 실기의 프레임률 | 기종 주사율 유지 [확인 필요]. 확정하지 않았다. 기종이 정해진 뒤 XR-06에서 수치를 정한다 |
| 웹 공유 | 번들 크기, 링크 → 첫 프레임 시간 | 데모 Halo의 공유 링크가 Fast 4G 프리셋에서 첫 프레임 3 s 이하, Slow 4G 프리셋에서 10 s 이하 |
| 결정론(멀티의 전제) | 같은 빌드 반복 실행의 해시 일치 | 플랫폼 태그(`engine.md` 5.4절 H1)가 같은 실행끼리 100%. 태그가 같으면 해시가 같다는 것은 아직 가정이고 #432가 검증한다 [확인 필요] |
| 플레이·판정 일치 | 기준 장면 2개에서 Jolt와 MuJoCo의 궤적 차이 | 잠정 허용 차이(`engine.md` 5.3절): 루트 강체 위치 차의 최댓값이 이동 경로 길이의 2% 이하, 자세 차의 최댓값이 0.1 rad 이하, 성공 조건의 충족 여부와 풀린 결합의 집합이 같다. 장면 2개·각 1회에 기댄 값이고 GD-02가 다시 정한다 |
| 물(수역 한정 힘) | MuJoCo 매질이 전역 값인지, 바디별 외력으로 준 부력의 평형 흘수 오차, 스텝당 비용(FL-01, 결과: `docs/research/fluids/mujoco-water.md` 8절) | 수계산 대비 1% 이하 |
| 고속 투사체·충돌 | 속도·시간 간격별 터널링 여부, 충돌 하중 [N] → 결합 해제의 해시 일치, 시간 간격에 따른 접촉력의 변화(CB-02) | 대결에 허용할 속도 범위를 측정 후 정한다. 확정하지 않았다(CB-02 뒤) |

위 표의 마지막 두 행은 PC-01로 더했다. A0-05가 `engine.md`를 쓸 때까지 CB-02가 끝나지 않으면 그 칸은 [확인 필요]로 두고 결정을 막지 않는다. FL-01은 끝났고 행의 내용은 `docs/research/fluids/mujoco-water.md` 8절이다.

정직한 약점: MuJoCo는 게임 물리가 아니다. 부품을 넣고 뺄 때마다 다시 컴파일해야 하고(조립 중 물리를 끄는 설계로 흡수한다), 다물체 성능과 브라우저 WASM의 성숙도는 [확인 필요]다. 웹이 문턱을 못 넘는 항목은 GD 트랙의 착수 조건이 된다. 두 번째 클라이언트는 공짜가 아니다. 화면과 입력을 한 번 더 만들어야 한다 [추정]. GD 트랙의 착수 조건은 `engine.md` 6.1절로 정해졌다(창업자 승인 2026-11-11): S1 Go 통과와 헤드리스 참조 클라이언트의 적합성 통과가 전제이고, 측정으로 참이 된 트리거(다물체 배속, 조종 지연, XR 프레임률) 하나가 있어야 연다. S1에는 시작하지 않는다.

"플랫폼 태그가 같으면 해시가 같다"는 아직 가정이고 #432가 검증한다 [확인 필요]. 기준 플랫폼은 Linux x86-64 고정 이미지 하나이고, 저장소에 커밋하는 기준 해시·기준 판정 수치와 서버 재시뮬은 그 플랫폼의 값만 쓴다. 태그가 다른 실행의 결과는 "재현 확인"이 아니라 "비교"로 표시한다. 따라서 공유 링크는 다시 시뮬하지 않고 기록된 궤적을 재생하며 번들에 태그를 싣는다 |

### 5.4 `docs/decisions/engine.md` 개요

A0-05가 이 목차대로 썼고(PR #434) 창업자가 승인했다(2026-11-11, #54 코멘트). 계획에 옮긴 내용은 17절이다.

1. **맥락:** 최종 버전의 요구 다섯 가지(PC-01로 물과 대결이 더해졌다)와 팀 규모.
2. **불변 결정:** Project JSON이 원본이다. 모든 편집은 Command다(MCP로도 노출). 판정은 코어의 MuJoCo 네이티브만 낸다. 클라이언트는 어댑터 경계 뒤에 있다.
3. **측정표:** 5.2의 요구별로 웹 + MuJoCo와 Godot + Jolt의 수치, 머신 사양, 명령, 시드. 물(FL-01)과 고속 투사체(CB-02) 행을 포함한다. 못 잰 칸은 [확인 필요].
4. **S1 주 클라이언트:** 결정과 근거, 포기한 것.
5. **플레이 물리와 판정 물리:** 갈릴 때의 화면 문구, 일치 시험 장면 묶음, 허용 차이.
6. **전환·병행 조건:** 어떤 측정값이면 GD 트랙을 시작하는가. 누가 언제 다시 재는가(M-05).
7. **기각한 대안:** Unity(독점), Bevy(에디터와 XR 미성숙 [추정])와 이유.
8. **재검토 시점과 승인 기록.**

## 6. REA 활용과 법적 선

REA는 코딩 에이전트가 네이티브 바이너리, JS/Electron 앱, .NET 어셈블리, 웹사이트, 런타임 동작을 들여다보게 하는 MCP + CLI다(MIT). .NET을 쉽게 풀어 준다는 점이 곧 위험이다. KSP와 Space Engineers가 정확히 그런 대상이다.

| 구분 | 대상 | 규칙 |
|---|---|---|
| **허용** | 우리 빌드 | 번들 크기, 런타임 동작, 성능 병목 점검 |
| **허용** | 허용적 라이선스 오픈소스(Godot 에디터, three.js editor, MuJoCo, Jolt) | 소스와 런타임 동작을 함께 연구한다. 라이선스 고지를 지킨다 |
| **조건부** | GPL·LGPL(Blender, FreeCAD) | 동작과 UX만 배운다. 코드를 옮기면 GPL 의무가 따라온다 |
| **조건부** | 공개 웹 서비스 | 화면에 보이는 동작과 UX의 벤치마킹까지만. 약관을 따르고 접근 제어를 우회하지 않는다 |
| **조건부** | 문서화되지 않은 파일 형식의 호환 분석 | 호환 목적의 예외 조항이 있더라도 EULA가 계약으로 막을 수 있다. 법률 자문 전에는 하지 않는다 [확인 필요] |
| **금지** | 독점 게임(KSP, Space Engineers, Juno, Besiege 등) | 디컴파일, 에셋 추출, 코드·부품 데이터 복제, DRM 우회. 풀어 본 코드를 참고하며 우리 코드를 쓰는 것도 금지한다 |

**클린룸 방식.** 독점 제품은 밖에서만 본다. 직접 플레이하고, 공개 문서와 개발자 발표를 읽고, 관찰한 동작을 `docs/research/benchmarks/<제품>.md`에 우리 말로 적은 뒤 그 문서만 보고 구현한다. 1~2인 팀은 관찰자와 구현자를 나눌 수 없으므로 "독점 바이너리는 열지 않는다"로 더 엄격하게 잡는다. REA 대상은 허용 목록 파일로 관리한다(A0-06). 상표·특허와 표현의 경계는 [확인 필요]이며 이 절은 법률 자문이 아니다.

**"가장 가까운 제품 위에 얹기"에 대한 답:** 에이전트 작업대 + 정직한 판정을 함께 가진 오픈소스 제품은 찾지 못했다 [추정]. 그래서 엔진 위에 얹는다.

정직한 한계: S1에서 "누구나"는 **보는 쪽**까지다. 제작은 로컬 설치가 필요하다. 헤드셋을 못 구하면 XR의 완성은 에뮬레이터 통과까지만 증명되고, 그 사실을 Go 자료에 적는다.

**데모 Halo:** ① 로켓 자동차 공중제비, 세 행성 비교. ② 같은 로버가 세 행성에서 경사를 오르는가. ③ (여력이 있으면) 만화 장면 한 건의 필요조건 판정.

## 11. 이슈 트리

이슈의 원본은 `issues.yaml`이다(에픽·이슈·하위 이슈 전부의 본문, 라벨, 마일스톤, 의존). 아래 표는 그 요약이다. 크기는 XS 2시간 이하, S 반나절, M 하루, F 창업자 작업이다. `prio:P0`은 단계 Go 경로, P1은 Go를 막지 않는 것, P2는 조건부·선택·이후 단계다. 마일스톤은 `S0 Process`, `S1-W01`~`S1-W12`, `S2`~`S5`다. 칸 안의 `a…(크기)`가 하위 이슈이자 PR 단위이고, 하위가 없는 이슈는 그 자체가 잎이다. 모든 잎에 "100% 완료" 8항목이 붙는다.

## 14. 결론

1. **지금(S0):** `legacy-v0` 태그를 찍고 새 트리를 연다. 나란히 세 가지를 한다. 최종 버전 기준으로 MuJoCo·웹·Godot + Jolt를 잰다(A0-01~03). 어댑터 경계를 문서로 고정한다(A0-04). 창업자는 `/design` 절차를 한 번 돌리고 헤드셋을 구한다(D0-01a, A0-07).
2. **만들 것:** 엔진 독립 코어(Project JSON, 명령 계층 + MCP, MuJoCo 판정) 위의 웹 Studio. 세 행성 평지, 부품 13종 안팎, 에이전트 변경안, 정직한 판정, Halo 내보내기, WebXR 헤드셋 조립. 12주(PC-02로 작업량이 14.0일 늘었다. 16.4절).
3. **가져갈 것:** 판정 자산(몬테카를로, 필요조건, 탐색, 비대칭)과 CAD, 캡처. 나머지는 태그에 두고 지운다.
4. **지킬 것:** 1회 실행을 판정이라 부르지 않는다. 에이전트는 판정하지 않는다. 플레이 물리는 판정이 아니다. 독점 게임의 바이너리는 열지 않는다.
5. **창업자가 정할 것:** 헤드셋 기종, 인터뷰 기능의 해석(H-05 착수 전). `engine.md`의 문턱과 결정은 정했다(2026-11-11, 아래 8번).
6. **PC-01(2026-11-10)로 더한 것:** 물은 S2의 저비용 층(부력·항력·부가질량과 라벨)과 S3의 연구 층으로, 대결은 안전선 안의 게임 모드로(S2, 실시간은 S4), 하드웨어 설계는 S2의 사양 내보내기와 S5의 키트로 넣는다. S1 범위는 그대로다. 창업자가 정할 것은 15.7절에 있다.
7. **PC-02(2026-11-11)로 더한 것:** KSP 클린룸 벤치마킹의 빈 곳 6건(추력중심 오버레이, 행성별 추력 대 중량비, 방사 대칭, 분리 부품과 분리 이벤트, 부품 정의가 빠진 프로젝트 열기, 파단의 시간 간격 불변 기준), '가져올 것' 가운데 S1에 없던 것, '다르게' 3건(재생 속도, 균일 중력 라벨, 파단 조각)을 S1 잎 25개로 넣었다. omp 14.0일과 승인본 1건이 늘었다. S1은 12주를 유지한다(창업자 결정, 16.5절).
8. **A0-05(2026-11-11)로 정한 것:** 창업자가 `docs/decisions/engine.md`를 승인했다. S1 주 클라이언트는 웹이고 화면의 물리는 코어의 실행을 그대로 재생한다. 코어와 판정은 MuJoCo 네이티브(버전 고정)다. 브라우저 WASM은 미리보기로만 쓴다. Godot + Jolt는 S1에 시작하지 않는다. 궤적 해시와 판정에는 플랫폼 태그를 붙이고 기준 플랫폼은 Linux x86-64 고정 이미지 하나다. 새 잎은 없고 기존 15개 항목의 DoD에 줄을 더했다(17절).

### 15.2 물·바다·유체

"모두 가능하게"가 정직하게 뜻할 수 있는 것은 아래 세 층이다.

| 층 | 무엇 | 단계 | 증거 등급 | 한계 |
|---|---|---|---|---|
| ① 저비용 층 | 수역(바다, 호수) 안의 강체에 부력, 수중 항력, 부가질량 근사를 준다. 물리 수면은 평면이고 파도는 렌더에만 있다 | S2 | L0~L2 그대로 쓴다. 가정표에 "근사" 라벨이 붙는다 | 잔잔한 물에 뜨거나 잠긴 강체까지만 맞는다 |
| ② 연구 층 | 입자·격자 유체(SPH, MPM)를 오프라인으로 돌려 결과를 재생한다 | S3 | "연구 실행(유체): 판정이 아닙니다" | Genesis, Taichi. GPU, macOS, 이 머신에서 도는지는 [확인 필요] |
| ③ 하지 않는다 | 완전한 CFD: 난류, 조파 저항, 프로펠러 유동, 공동 | — | "모델 밖" | OpenFOAM은 GPL이고 FluidX3D는 비상업 라이선스다 [확인 필요] |

**① 저비용 층의 내용**

| 요소 | 방식 | 이슈 |
|---|---|---|
| 수역 | World에 놓는 영역(범위, 수면 높이, 깊이, 액체 참조). 편집은 Command다 | FL-02b |
| 부력 | 수역은 수평 영역을 바닥(수면 높이 − 깊이)과 수면 사이로 세운 기둥이다. 충돌 프록시와 이 기둥의 교집합으로 잠긴 부피를 구하고 그 도심을 부심으로 삼아 바디별 힘으로 준다. 측면 밖, 바닥 아래, 수면 위는 물이 아니다 | FL-03a |
| 수중 항력 | W-03b의 집중 항력을 잠긴 부분에는 액체 밀도로 준다 | FL-03b |
| 부가질량 | 형상 계수(인용, 없으면 `추정`)를 완전 잠김 기준으로 적용한다. 끌 수 있다 | FL-03c |
| 부유 정역학 | 실행 전에 뜨는지, 흘수, 초기 복원성을 계산해 경고한다(L0) | FL-03d |
| 수중 추진기 | 추력 곡선을 사양으로 갖는 부품. 프로펠러 유체역학은 모델 밖이다 | FL-03e |
| 파도 | 렌더 전용. 켜도 궤적 해시가 바뀌지 않는다는 테스트를 둔다 | FL-04a |

**MuJoCo에 대해 확인한 것 (FL-01, 4.0.0, `docs/research/fluids/mujoco-water.md`).** MuJoCo의 매질 밀도와 점성(`option`의 `density`, `viscosity`)은 모델 전역 값이어서 한 장면 안에서 공기와 물을 영역으로 나눌 수 없다(`시뮬`: 같은 속도의 물체가 z=+5와 z=−5에서 유체력이 같다). 부력은 내장돼 있지 않다. 타원체 유체 모델은 항력(지오메트리별 계수 5개)을 주지만 **가속도에 비례하는 부가질량 항(−m_A·v̇)은 4.0.0 소스에서 꺼져 있다**(`인용`). 속도끼리 엮이는 항만 남는다. 역시 전역 매질이고 수면과 부분 잠김을 모른다. 그래서 수역 한정 부력, 수중 항력, 부가질량은 모두 바디별 외력(또는 질량 조정)으로 직접 준다. 측정 결과: 상자의 평형 흘수 오차는 수계산 대비 최대 2.4×10⁻⁴ %(`xfrc_applied`)와 9.0×10⁻⁶ %(`mjcb_passive`)였고(시드 0, 상자 8개, `시뮬`), 부가질량은 관성 증가 + 중력 보상이 구 하나의 완전 잠김에서 정확하고 안정했으며 직전 스텝 가속도에 비례한 힘은 m_a/m ≥ 1에서 발산했다. W-03b(집중 항력)는 매질 밀도를 위치로 조회하는 함수로 두는 것을 권고받았다. 아직 검증하지 않은 것은 [확인 필요]로 남긴다: 구 외 형상의 잘라내기, 부분 잠김과 관절 트리의 부가질량, 명시적 힘의 시간 간격 안정 한계, RK4에서의 힘 주기(각각 FL-03a~d의 몫).

**행성별**

| 행성 | 표면의 액체 | 수역을 놓으면 |
|---|---|---|
| 지구 | 해수와 담수. 밀도와 점성은 출처 있는 데이터 파일에 둔다(FL-02a) | `인용` 배지 |
| 화성 | 표면에 안정한 액체 물이 없다(기압이 낮다). 출처는 FL-02a에서 붙인다 [확인 필요] | 액체를 사용자가 선언한다. `사용자 선언` 배지와 자막이 붙는다 |
| 달 | 대기가 없어 표면에 액체가 없다. 출처는 FL-02a에서 붙인다 [확인 필요] | 화성과 같다 |

화성이나 달에 수역을 놓는 것을 막지는 않는다. 중력은 그 행성의 값을 쓰고, 판정 카드와 Halo 자막에 "이 행성 표면에 이 액체가 있다는 근거는 없습니다(사용자 선언)"가 자동으로 들어간다(FL-02c). 물이 아닌 임의의 액체도 밀도와 점성을 선언하면 같은 경로로 쓴다.

**라벨.** 값 배지 5종(`시뮬` `인용` `기본값` `사용자 선언` `추정`)은 그대로 두고 새 배지를 만들지 않는다. 유체가 근사라는 사실은 가정표의 모델 라벨로 표시한다(W-03b의 "근사: 집중 항력"과 같은 방식이다).

| 라벨 | 뜻 |
|---|---|
| `근사: 부력(프록시의 잠긴 부피)` | 형상이 아니라 충돌 프록시의 부피로 계산했다 |
| `근사: 수중 항력(집중 계수)` | 형상별 계수 하나로 항력을 준다. 유동을 풀지 않는다 |
| `근사: 부가질량(형상 계수, 완전 잠김 기준)` | 부분 잠김에서도 같은 계수를 쓴다 |
| `시각 전용: 파도` | 화면의 파도는 물리에 들어가지 않는다 |
| `연구 실행(유체): 판정이 아닙니다` | 입자 유체 결과. p_success에 섞지 않는다 |

수역이 있는 프로젝트의 판정 카드 "이 모델이 보지 않는 것"에는 파도 하중, 조파 저항, 슬로싱, 공동이 자동으로 들어간다(FL-04b). 수계산 대조(흘수, 종단속도, 진동 주기)는 같은 근사식끼리의 비교이므로 구현 검증이지 현실과의 대조가 아니다. 물에 대한 실측은 0건이다.

**② 연구 층.** 후보는 Genesis(30.2k, Apache-2.0. SPH·MPM 등 솔버의 범위는 [확인 필요])와 Taichi(28.5k, Apache-2.0. MPM 예제가 있다)다. 조사는 기존 T-06이 맡고 FL-06~08이 실행기, 등급 표시, 대조 1건을 잇는다. 결과는 해상도와 실행 횟수에 기대고 수렴을 확인하지 않은 것이므로 "연구 실행"으로 따로 표시한다. 등급을 올리는 조건 [제안]은 해상도 두 단계에서의 수렴과 출처 있는 공개 사례 1건과의 대조다. 그 전에는 L2 판정에 섞지 않는다. 이 머신(SSD 여유 25 GB 안팎)에서 설치와 실행이 되는지는 모르며 자원 가드를 통과할 때만 돌린다(15.6절).

### 15.3 대결 모드

대결은 새 물리가 아니다. S1의 강체, 집중 항력, 결합부 파단과 S2의 미션 정의 위에 진영과 승패 규칙을 얹은 게임 모드다. 상상한 설계가 서로 겨루는 Halo와 게임이 목적이다.

| 요소 | 정의 | 표시 | 이슈 |
|---|---|---|---|
| 진영 | 두 진영의 설계(차량, 배, 발사기, 장갑판), 시작 배치, 승리 조건, 예산. MissionDef(M-01)를 확장한 MatchDef | — | CB-06a |
| 투사체 | 질량, 지름, 항력 계수. 발사된 뒤에는 중력과 집중 항력만 받는다 | `근사: 집중 항력` | CB-04b, c |
| 발사기 | "선언 발사 에너지" 수치 하나. 발사 속도는 에너지와 투사체 질량에서 계산하고 반동을 준다. 화약과 연소의 모델이 없다 | `사용자 선언` 또는 `기본값` | CB-04b |
| 충돌과 파괴 | 결합부에 걸린 하중 [N]이 임계 하중 [N](강도 [Pa] × 단면적 [m²], X-04a)을 넘으면 결합이 풀린다(X-04b). 충돌 때의 하중은 고정된 물리 시간 창으로 평균한 구속력으로 잡고, 충격량 [N·s]을 임계와 직접 비교하지 않는다. 시간 간격을 바꿔도 풀리는 결합이 같아야 한다. 구동 부품이 떨어지면 그 기능을 잃는다 | "단순화 모델", 창 길이는 `기본값` | CB-05 |
| 장갑 | 재료와 두께를 갖는 판. 임계 하중 [N] = 재료 강도 [Pa] × 단면적 [m²](X-04a)이고 판에 걸린 하중 [N]과 비교한다 | `게임 규칙: 장갑 파단` | CB-04d |
| 탐지 | 거리와 시선(가림)의 규칙. 센서를 모델하지 않는다 | `게임 규칙: 탐지` | CB-06b |
| 제어 | 수동 조종 또는 저장된 제어 스케줄. 자동 추적, 유도, 자동 조준은 없다 | — | CB-06c |
| 대결 판정 | 한 판의 결과는 A 승, B 승, 무승부다. 시간초과는 기본이 무승부이고 MatchDef의 `on_timeout`으로 바꿀 수 있다. 두 진영이 모두 스케줄일 때 가정을 흔든 몬테카를로로 A 승률, B 승률, 무승부율과 95% CI를 낸다. 분모는 무승부를 포함한 유효한 모든 판이다. 유효한 판이 0이면(전부 시뮬 오류) "판정 불가"로 표시하고 승률·CI·우세를 내지 않는다. "우세"는 두 승률 차이의 CI가 0을 포함하지 않을 때만 표시한다. 수동 대결 한 판은 "1회 실행"이다 | L2 / L1 | CB-06a, d |
| 실시간 대결 | S4. N-05의 서버 물리 위에서 하고 "플레이 물리"로 표시한다 | — | CB-10~12 |

바다 위의 대결은 15.2절의 저비용 층과 합친 것이다(CB-09b).

> **안전선(대결 모드).** Kinetra는 게임 수준의 대결 물리만 다룬다: 운동에너지 투사체의 탄도(중력과 항력), 충돌, 결합부 파단, 재료 × 두께로 정한 장갑판의 파단 임계, 규칙으로 추상화한 탐지. 아래 다섯 가지는 제공하지 않는다. 에이전트의 답, 카탈로그, 문서, 내보내기 어디에서도 마찬가지다.
>
> 1. 폭약, 추진제, 점화제의 조성·배합·제조법과 그 에너지 화학 계산.
> 2. 탄두, 신관, 기폭 장치의 설계.
> 3. 실제 무기에 쓸 수 있는 유도, 추적, 조준, 사격 통제 알고리즘.
> 4. 작동하는 무기나 탄약을 만드는 방법: 도면, 부품 목록, 가공·조립 지침.
> 5. 대결 부품(발사기, 투사체, 장갑판)의 실물 내보내기. BOM, STEP·STL, 하드웨어 사양서, S5 키트는 이 부품을 뺀다.
>
> 대결의 결과는 "게임 물리"다. 실제 무기의 성능을 예측하지 않으며 화면과 영상에 그렇게 표시한다.

| 선 안쪽의 예 | 선 바깥의 예 |
|---|---|
| 선언 발사 에너지로 구를 쏘는 발사기, 세 행성에서의 사거리 비교 | "이 탄에 넣을 화약의 배합과 양을 계산해 줘" |
| 두께를 바꿔 가며 판이 버티는지 보는 대결 | "명중률을 높이는 유도 로직을 짜 줘" |
| 조준 미리보기 선(같은 모델의 1회 실행 표시) | "이 발사기를 실제로 만들 도면과 부품 목록을 줘" |
| 기존 냉가스 추력기(추진제 질량과 인용된 비추력만 쓴다. 조성과 연소는 원래 모델 밖이다) | 실존 무기 체계의 이름과 제원을 재현한 카탈로그 항목 |

**왜 긋는가**

1. **법과 수출통제 [확인 필요, CB-03].** 무기와 화약류의 제조 방법을 알리는 일을 제한하는 법(한국의 총포·화약류 관련 법), 무기 관련 기술의 이전을 통제하는 제도(한국의 전략물자 제도, 미국의 ITAR·EAR)가 있는 것으로 안다. 공유 링크와 내보내기 파일은 국경을 넘는다. 구체 조항과 우리에게 적용되는지는 확인하지 않았다. 이 절은 법률 자문이 아니다.
2. **플랫폼 [확인 필요, CB-03].** 에이전트가 쓰는 LLM 제공사의 이용 정책, 영상과 호스팅 플랫폼의 정책이 무기 제작 지원을 금지하는 것으로 안다. 어기면 대결만이 아니라 에이전트와 Halo 공개 전체가 막힐 수 있다.
3. **V1.** 장갑 파단 임계와 선언 발사 에너지는 검증된 무기 모델이 아니다. 이것을 무기 성능이라 부르면 약한 증거를 강하게 말하는 것이다.
4. **V2의 범위.** "상상에서 현실까지"는 대결에 대해서는 상상(Halo, 게임)에서 멈춘다. 현실로 이어지는 것은 차량, 배, 로버 같은 플랫폼의 하드웨어 사양까지다.
5. **팀 규모.** 1~2인 팀은 이 영역의 법률 검토와 사후 대응을 감당할 수 없다 [추정].

**어떻게 강제하는가**

### 15.6 개발 자원 가드

창업자 보고: 개발 머신의 SSD 여유가 25 GB 안팎이고 스왑이 자주 가득 찬다. WebXR 에뮬레이터는 무겁지만 스왑과 SSD 여유를 보면서 진행하기로 했다. 헤드셋은 아직 없고 창업자가 구매한다(A0-07은 그대로다).

- 실행 전에 `tools/dev/resource_guard.py`(P0-09)가 SSD 여유, 스왑 사용량, 메모리 압력을 확인한다. 임계의 기본값 [제안]은 SSD 여유 10 GB 미만이면 차단, 스왑 사용률 90% 이상이면 경고, 메모리 압력이 위험 단계면 차단이다. P0-09에서 이 머신의 실측으로 다시 정한다.
- 차단되면 정리 절차(임시 worktree, uv·pnpm 캐시, Playwright 브라우저, 스파이크 산출물)를 따른 뒤 다시 잰다.
- 가드가 생기기 전에는 실행 전에 직접 확인해 PR에 수치를 적는다.
- 연구 층(Genesis, Taichi)은 가드를 통과할 때만 설치하고 돌린다. 안 되면 다른 머신이나 클라우드를 쓸지 창업자가 정한다.

### 17.4 일정 영향
