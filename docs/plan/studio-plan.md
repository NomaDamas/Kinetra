## 1. 한 줄 정의, 북극성, 핵심 가치

**정의:** 빈 행성 평지의 작업대에서 에이전트와 함께 무엇이든 조립하고, 그 행성의 물리로 돌려 보고, 가정과 확률이 붙은 Halo(영상 + 플레이 링크)로 내보내는 스튜디오.

**북극성:** 누구든 상상한 물건을 직접 만들어 물리 세계에서 돌려 보고, 정직한 판정과 함께 남에게 보여 준다. 경로는 **생각 → 상상 → 실제 물리 세계**다.

핵심 가치의 원문은 아래 다섯 줄이다. 이슈와 PR은 이 문장을 그대로 인용한다(`docs/plan/values.md`).

- **V1 정직한 판정** — 판정은 시뮬과 몬테카를로만 한다. 확률, 가정, 한계를 숨기지 않는다. 1회 미리보기 실행을 판정이라 부르지 않는다.
- **V2 상상에서 현실까지** — 모든 기능은 생각 → 상상 → 실제 물리 세계의 거리를 줄여야 한다.
- **V3 한 번에 100%** — 작은 단위를 증거와 함께 완전히 끝낸다. 부분 완성은 미완성이다.
- **V4 보여줄 수 있는 결과** — 결과는 시뮬 리플레이 그대로 영상과 플레이 링크가 된다. 연출은 카메라·조명·편집만 바꾸고 궤적은 바꾸지 않는다.
- **V5 깨끗한 출처** — 수치, 부품, 에셋은 출처와 라이선스가 기록된 것만 쓴다. 사용자가 선언한 값과 가져온 에셋은 배지로 구분한다.

판단: V2·V3는 그대로다. V1은 마지막 문장을, V5는 둘째 문장을 보강했고, V4는 연출의 허용 범위를 명시했다. 가치는 늘리지 않는다. "에이전트는 제안하고 사람이 수락한다"는 가치가 아니라 제품 규칙(4.4)이다.

## 3. 제품 정의: Kinetra Studio

Halo Studio가 곧 제품이다. Halo는 그 산출물 한 편을 가리킨다.

| 요소 | 정의 |
|---|---|
| 작업대 | 평지 위 조립 공간. 조립 중에는 물리를 끄고, 실행할 때 모델을 컴파일한다 |
| 행성 | 지구·화성·달의 **허허벌판**. 행성이 정하는 것은 중력, 대기 밀도, 지면 마찰 분포, 하늘·조명뿐이다. 값은 출처가 붙은 데이터 파일에 둔다. 구형 행성, 궤도, DEM 지형은 없다 |
| 라이브러리 | ① 기본 부품(파라메트릭, 사양 출처 있음) ② 내 것(저장한 조립체, 가져온 glb) ③ 생성(생성 3D는 시각 스킨 전용, S2) |
| 에이전트 | 텍스트·음성 의도를 편집 명령 묶음으로 바꿔 제안한다. 사람이 미리 보고 수락한다 |
| 물리 설정 | 강체 질량·무게중심·관성, 관절과 한계, 액추에이터, 재질, 파단 임계, 제어 스케줄 |
| 실행 모드 | 시뮬(S1) → 미션(S2) → 게임(S2). 같은 프로젝트에 목표·예산·점수 규칙을 얹어 가는 구조다 |
| Halo 출력 | 리플레이 영상(mp4) + 같은 프로젝트가 열리는 공유 플레이 링크. 판정 자막이 자동으로 붙는다 |

**인터뷰는 선택 기능이다.** Halo를 만들 때 에이전트가 의도(무엇을 보여 줄지, 성공 조건)를 몇 문항으로 묻는 단계이고 건너뛸 수 있다. 이 해석은 [추정]이며 창업자 확인이 필요하다.

## 4. UX/UI 설계

### 4.1 화면 구조

```
┌─────────────────────────────────────────────────────────────────────────┐
│ 프로젝트명 │ 행성 [지구|화성|달] │ [조립|실행|판정|Halo] │ 증거 배지 │ 공유 │
├───────────┬─────────────────────────────────────────┬───────────────────┤
│ 라이브러리 │                                         │ 인스펙터          │
│  기본 부품 │        3D 뷰포트 (작업대 / 평지)        │  강체: 질량·COM   │
│  내 것     │   기즈모 · 스냅 · 고스트(변경안)        │  관절 · 한계·파단 │
│  가져오기  │   질량중심 · 지지 다각형 오버레이       │  액추에이터·제어  │
│  (생성)    │                                         │  재질 · 값 배지   │
├───────────┴─────────────────────────────────────────┴───────────────────┤
│ 에이전트 바: [🎤] 입력 ▸ 변경안 카드 [미리보기][수락][부분][거절]        │
│ 타임라인: ▶ ⏸ ↺ │ 실패 표식 ▲ 파단 ✕ │ 판정 카드 열기                    │
└─────────────────────────────────────────────────────────────────────────┘
```

모드는 네 개다. **조립**(물리 꺼짐), **실행**(미리보기 1회, 수동 조종), **판정**(탐색 + 몬테카를로), **Halo**(카메라·자막·내보내기). 뷰포트가 항상 중심이고 패널은 접을 수 있다.

### 4.2 핵심 플로우

**A. 로켓 자동차 공중제비 Halo (텍스트·음성 중심)**
1. 새 프로젝트 → 지구 평지.
2. "1.3톤 차체에 냉가스 추력기를 달아 점프대에서 한 바퀴 돌고 바로 착지하게 해 줘."
3. 에이전트가 변경안 카드 넷을 낸다: 차체와 바퀴 / 추력기 배치 / 점프대 소품 / 성공 조건(회전각, 착지 자세·속도). 카드마다 고스트와 질량·무게중심 변화가 보인다. kN급 추력기는 카탈로그에 없으므로(최대 8.9 N) "카탈로그 밖 · 사용자 선언" 배지가 붙는다.
4. 사용자가 3D에서 추력기를 기즈모로 옮기고 인스펙터에서 추력을 고친다.
5. 실행 → 회전 부족으로 실패 → 타임라인 표식.
6. 탐색(CMA-ES가 분사 스케줄을 찾는다) → 성공 사례 발견 또는 `NOT_FOUND_IN_BUDGET`(약한 증거).
7. 판정 → p_success와 신뢰구간, 판정을 뒤집는 가정 1위.
8. 달·화성으로 전환해 다시 판정하고 비교한다.
9. Halo → 카메라 선택 → 자막 자동 → mp4 + 링크.

기존 측정값은 그대로 영상에 들어간다: 노즐당 8 kN에서 15.2% [12.3, 18.6], 추력 잡음 ±10%에서 0.8%. 차체는 자체 제작이고 상표는 쓰지 않는다.

**B. 화성 로버 (마우스 중심)**
1. 화성 평지에 경사로 소품을 놓는다.
2. 라이브러리에서 빔·휠·모터를 끌어 놓는다. 스냅 포인트가 맞으면 붙고 틀리면 거부된다.
3. 인스펙터에서 재질을 바꾸면 질량과 무게중심이 바로 갱신된다.
4. 정역학 검사가 "이 경사에서 전복"을 실행 전에 경고한다. 실행 모드에서 키보드로 몰아 본다.
5. 판정: 지면 마찰을 분포로 흔든 등판 성공 확률. 같은 로버를 지구·달에서 나란히 돌린다.

**C. 만화 장면 검증 (에이전트 대화 중심)**
1. "사람이 자동차를 30 m 던질 수 있어?"
2. 에이전트가 장면을 질량·속도·높이·시간으로 옮기며 빠진 값을 묻는다(선택 인터뷰).
3. 필요조건 스크린이 필요 에너지·출력을 계산해 `INFEASIBLE_NECESSARY_CONDITION` 카드를 낸다. 비교 기준(사람 근육 출력)은 출처가 있어야 하고 없으면 [확인 필요]로 표시한다.
4. 강체로 되는 부분(투사체, 충돌)만 시뮬한다. 기·빔·변신은 "모델 밖"으로 분류한다.
5. 원작 캐릭터 외형은 쓰지 않는다. S1에는 필요조건 카드와 투사체 시뮬만 넣고 장면 유형 확장은 S3이다.

### 4.3 입력 모드

모든 입력은 같은 **편집 명령(Command)**으로 바뀐다. 되돌리기, 고스트 미리보기, 리플레이가 입력 수단과 무관하게 동작하는 이유다.

| 모드 | 맡는 일 | S1 범위 | 한계 |
|---|---|---|---|
| 텍스트 | 의도, 수치, 일괄 변경 | 완성 | 공간 위치 지정이 모호하다 |
| 음성 | 손이 바쁠 때의 텍스트 대체. 헤드셋 안에서는 주 입력 | 받아쓰기 → 인식문 확인 → 텍스트와 같은 경로 | 한국어 인식 품질 [확인 필요]. 삭제류 명령은 확인 단계를 둔다 |
| 마우스·키보드 | 정밀 배치, 기즈모, 스냅, 수치 입력 | 완성 | — |
| XR(WebXR 헤드셋) | 잡기, 놓기, 돌리기, 스냅 결합, 크기 가늠 | **완성**(창업자 확정) | 정밀 수치가 안 된다. 스냅과 음성으로 보완한다. 시험용 헤드셋 확보는 [확인 필요] |

**헤드셋 안에서의 조립.** 손 추적이나 컨트롤러로 부품을 잡아 옮기고 돌린다. 가까운 호환 스냅 포인트에 고스트가 뜨고 놓으면 붙는다. 손목 팔레트에서 새 부품을 꺼내고, 누르고 말하기로 에이전트에게 요청하면 변경안의 고스트와 카드가 공간에 뜬다. 잡고 있는 부품이 "이것"의 문맥이 된다. 작업대는 탁상 크기와 실물 크기를 오간다(보기만 바뀌고 치수는 그대로다). 증거 단계 배지와 "1회 실행" 표시는 공간에도 있다. 개발과 CI는 WebXR 에뮬레이터로 하고, 실기 시험은 창업자 작업(F)이다. 웹캠 손 추적(MediaPipe)은 S2로 미뤘다.

### 4.4 에이전트와의 협업

- **제안 → 미리보기 → 수락.** 변경안은 명령 묶음이다. 3D에는 반투명 고스트, 카드에는 수치 변화(질량, 무게중심, 부품 수)가 뜬다. 수락, 부분 수락, 거절, 되돌리기가 된다.
- **3D에서 직접 수정.** 사용자가 고른 부품이 에이전트의 문맥이 된다("이것만 더 가볍게").
- **검증기.** 겹침, 공중에 뜬 부품, 무효 스냅, 스키마 위반은 화면에 오기 전에 거부되고 에이전트가 정해진 횟수 안에서 다시 시도한다.

| 에이전트가 한다 | 하지 않는다 |
|---|---|
| 부품 추가·배치·결합, 파라미터·재질 변경 | 판정 선언 |
| 제어 스케줄 초안, 탐색·판정 실행 요청 | 행성 상수·물성 DB 변경 |
| 롤아웃 수치만 인용한 실패 설명 | 카탈로그에 없는 사양을 있는 것처럼 쓰기 |
| 가져온 에셋의 프록시·질량 제안(추정 배지) | 물리 부품의 형상을 생성 메시로 만들기 |

**인스펙터 항목:** 강체(질량, 무게중심, 관성; 계산값인지 선언값인지), 관절(종류, 축, 한계, 파단 임계), 액추에이터(토크-속도 곡선 또는 추력 곡선, 추진제 질량), 재질(밀도, 항복강도, 마찰), 제어 스케줄. 모든 수치 옆에 배지가 붙는다: `시뮬` `인용` `기본값` `사용자 선언` `추정`.

### 4.5 물리 판정 표시

증거는 네 단계이고 상단 배지가 현재 단계를 보여 준다.

| 단계 | 화면 문구 | 근거 |
|---|---|---|
| L0 조립 | 질량, 무게중심, 정역학 경고 | 해석 계산 |
| L1 미리보기 | "1회 실행. 판정이 아닙니다" | 명목 모델 1회 |
| L2 판정 | `FEASIBLE_FOUND` + p_success·95% CI / `INFEASIBLE_NECESSARY_CONDITION` / `NOT_FOUND_IN_BUDGET`(약함) / 모델 밖 | 탐색 + 몬테카를로 |
| L3 실측 | "실물 검증 없음" | 현재 0건이다. 숨기지 않는다 |

판정 카드에는 가정표(값, 분포, 출처, 신뢰도), 민감도(어느 가정이 판정을 뒤집는가), "이 모델이 보지 않는 것"(CFD, 연소, FEM, 열)이 함께 붙는다. 색은 성공·실패가 아니라 증거의 강도를 나타낸다. 이 원칙은 과거 판정이 가정에 따라 13%↔77%로 흔들린 데서 나왔다.

### 4.6 행성 전환, 실패 리포트, Halo

- **행성 전환:** 상단 한 번. 설계는 두고 상수만 바꿔 다시 컴파일한다. 이전 판정은 무효로 표시된다. 비교 보기는 세 행성을 나란히 재생한다.
- **실패·파단:** 파단은 FEM이 아니라 결합부 임계값(물성 × 단면, "단순화 모델" 표시)이다. 리포트에는 원인(전복, 슬립, 토크 부족, 추진제 고갈, 파단), 타임라인 시점, 임계 대비 여유가 나온다.
- **Halo 영상:** 질문 → 시도 → 판정 공개 → 엔드카드. p_success, CI, 핵심 가정이 자막으로 들어간다. 판정 없이 내보내면 "판정 없음: 1회 실행"이 남는다. 성공 장면이 표본 중 하나라는 것도 표시한다.

## 5. 기술 아키텍처 결정

### 5.1 원칙: 최종 버전을 막지 않는 구조

창업자의 기준은 "최종 버전에 도달할 수 있는 선택"이다. 최종 버전은 열린 세계, 멀티와 파괴, XR, 공유 링크, 실시간 플레이를 모두 요구한다. 어떤 단일 클라이언트도 이 전부에서 가장 낫지 않으므로, 엔진을 하나 고르는 대신 **갈아 끼울 수 있는 경계**를 먼저 고정한다.

```
클라이언트(갈아 끼움)              코어(고정, 엔진 독립)
 웹: three.js/R3F + WebXR  ─┐      Project JSON(원본)
 Godot + Jolt (S2+, 조건부) ─┼─ 어댑터 ─ 명령 계층(Command) + 검증기 ─ MCP 서버
 헤드리스 참조 클라이언트   ─┘  경계     컴파일·실행·판정 서비스: MuJoCo 네이티브(권위)
```

- **코어가 쥐는 것:** 프로젝트, 명령의 검증과 적용, 컴파일, 실행, 판정. 판정은 어떤 클라이언트에서도 코어의 MuJoCo 네이티브만 낸다.
- **클라이언트가 쥐는 것:** 렌더, 입력 → Command, 실행 스트림 재생. 실시간 플레이를 위해 클라이언트가 자체 물리(Jolt)를 돌릴 수 있지만, 그 결과는 "플레이 물리"로 표시하고 판정이라 부르지 않는다.
- **어댑터 경계의 계약 다섯 가지:** 문서 구독, 명령 발행, 실행 스트림 프레임, 에셋 로딩, 입력 매핑. 헤드리스 참조 클라이언트와 MCP 서버가 S1에서 이 경계를 실제로 쓰므로, 경계가 웹에 묶였는지는 S1 안에서 드러난다(C-05).

정직한 비용: 경계를 두면 S1이 느려진다(프로토콜, 적합성 테스트). 그리고 플레이 물리와 판정 물리가 갈리는 순간 V1을 지키는 일이 표시 문구와 일치 시험에 달리게 된다.

### 5.2 클라이언트 비교

| 기준 | 웹(three.js/R3F) | Godot + Jolt | Unity | Bevy |
|---|---|---|---|---|
| Claude Design 핸드오프 | HTML → React 직접 | Control 노드로 다시 옮겨야 한다 | 같음 | 같음 |
| 공유 플레이 링크 | 설치 없음 | 웹 내보내기 제약(C# 불가, SharedArrayBuffer) | WebGL 빌드, 무겁다 [추정] | WASM 가능 |
| 판정 엔진과의 일치 | 코어 실행을 그대로 재생 | 플레이(Jolt)와 판정(MuJoCo)이 갈린다 | 갈린다 | 갈린다 |
| XR | WebXR(pmndrs/xr 2.6k) | OpenXR, 더 강하다 [확인 필요] | 가장 성숙 [추정] | 초기 |
| 다물체, 큰 월드, 파괴, 실사 | 약하다 | 강하다 | 강하다 | 중간 |
| 실시간 멀티 | 서버 물리에 의존 | 클라이언트 예측 가능 | 가능 | 직접 구현 |
| 런타임 작업대 | 직접 만든다 | 에디터는 개발자용이라 역시 직접 만든다 [추정] | 같음 | 에디터 없음 |
| 기존 코드 | R3F 리플레이, 스트리밍 | 새로 쓴다 | 새로 쓴다 | 새로 쓴다 |
| 라이선스 | MIT | MIT | 독점. 엔진을 고칠 수 없다 | Apache |

**권고: S1 주 클라이언트는 웹(three.js 118.0k + R3F 33.6k), 코어 물리는 MuJoCo(17.1k) 네이티브. Godot + Jolt는 S2 이후 열린 세계·멀티용 두 번째 클라이언트 트랙(GD)으로 남긴다.** 최종 확정은 S0 스파이크 뒤 `docs/decisions/engine.md`에서 한다.

웹을 S1에 권하는 근거는 셋이다. ① Claude Design의 산출물이 그대로 구현 재료가 된다. ② 플레이 링크가 설치 없이 열린다. ③ 코어의 실행을 그대로 재생하므로 S1에는 플레이와 판정이 갈리지 않는다.

**스파이크의 기준은 S1이 아니라 최종 버전의 요구다.** 수치 문턱은 모두 [제안]이고 engine.md에서 창업자가 확정한다.

| 요구 | 측정(A0-01~03) | 문턱 [제안] |
|---|---|---|
| 다물체와 파괴 | 강체 200 / 1,000 / 5,000개, 결합 해제 100건의 실시간 배속(MuJoCo, Jolt 각각) | S1은 200개 실시간. 최종 버전 후보는 1,000개 실시간 |
| 실시간 플레이 | 조종 입력 → 화면 지연, 포즈 스트림 대역폭 | 로컬 100 ms 이하 |
| XR | 에뮬레이터와 실기의 프레임률 | 기종 주사율 유지 [확인 필요] |
| 웹 공유 | 번들 크기, 링크 → 첫 프레임 시간 | 측정 후 정한다 |
| 결정론(멀티의 전제) | 같은 빌드 반복 실행의 해시 일치 | 100% |
| 플레이·판정 일치 | 기준 장면 2개에서 Jolt와 MuJoCo의 궤적 차이 | 측정 후 정한다 |

정직한 약점: MuJoCo는 게임 물리가 아니다. 부품을 넣고 뺄 때마다 다시 컴파일해야 하고(조립 중 물리를 끄는 설계로 흡수한다), 다물체 성능과 브라우저 WASM의 성숙도는 [확인 필요]다. 웹이 문턱을 못 넘는 항목은 GD 트랙의 착수 조건이 된다. 두 번째 클라이언트는 공짜가 아니다. 화면과 입력을 한 번 더 만들어야 한다 [추정].

### 5.4 `docs/decisions/engine.md` 개요

A0-05가 이 목차대로 쓴다. 창업자 승인 대상이다.

1. **맥락:** 최종 버전의 요구 다섯 가지와 팀 규모.
2. **불변 결정:** Project JSON이 원본이다. 모든 편집은 Command다(MCP로도 노출). 판정은 코어의 MuJoCo 네이티브만 낸다. 클라이언트는 어댑터 경계 뒤에 있다.
3. **측정표:** 5.2의 요구별로 웹 + MuJoCo와 Godot + Jolt의 수치, 머신 사양, 명령, 시드. 못 잰 칸은 [확인 필요].
4. **S1 주 클라이언트:** 결정과 근거, 포기한 것.
5. **플레이 물리와 판정 물리:** 갈릴 때의 화면 문구, 일치 시험 장면 묶음, 허용 차이.
6. **전환·병행 조건:** 어떤 측정값이면 GD 트랙을 시작하는가. 누가 언제 다시 재는가(M-05).
7. **기각한 대안:** Unity(독점), Bevy(에디터와 XR 미성숙 [추정])와 이유.
8. **재검토 시점과 승인 기록.**

## 6. REA 활용과 법적 선

REA는 코딩 에이전트가 네이티브 바이너리, JS/Electron 앱, .NET 어셈블리, 웹사이트, 런타임 동작을 들여다보게 하는 MCP + CLI다(MIT). .NET을 쉽게 풀어 준다는 점이 곧 위험이다. KSP와 Space Engineers가 정확히 그런 대상이다.

| 구분 | 대상 | 규칙 |
|---|---|---|
| **허용** | 우리 빌드 | 번들 크기, 런타임 동작, 성능 병목 점검 |
| **허용** | 허용적 라이선스 오픈소스(Godot 에디터, three.js editor, MuJoCo, Jolt) | 소스와 런타임 동작을 함께 연구한다. 라이선스 고지를 지킨다 |
| **조건부** | GPL·LGPL(Blender, FreeCAD) | 동작과 UX만 배운다. 코드를 옮기면 GPL 의무가 따라온다 |
| **조건부** | 공개 웹 서비스 | 화면에 보이는 동작과 UX의 벤치마킹까지만. 약관을 따르고 접근 제어를 우회하지 않는다 |
| **조건부** | 문서화되지 않은 파일 형식의 호환 분석 | 호환 목적의 예외 조항이 있더라도 EULA가 계약으로 막을 수 있다. 법률 자문 전에는 하지 않는다 [확인 필요] |
| **금지** | 독점 게임(KSP, Space Engineers, Juno, Besiege 등) | 디컴파일, 에셋 추출, 코드·부품 데이터 복제, DRM 우회. 풀어 본 코드를 참고하며 우리 코드를 쓰는 것도 금지한다 |

**클린룸 방식.** 독점 제품은 밖에서만 본다. 직접 플레이하고, 공개 문서와 개발자 발표를 읽고, 관찰한 동작을 `docs/research/benchmarks/<제품>.md`에 우리 말로 적은 뒤 그 문서만 보고 구현한다. 1~2인 팀은 관찰자와 구현자를 나눌 수 없으므로 "독점 바이너리는 열지 않는다"로 더 엄격하게 잡는다. REA 대상은 허용 목록 파일로 관리한다(A0-06). 상표·특허와 표현의 경계는 [확인 필요]이며 이 절은 법률 자문이 아니다.

**"가장 가까운 제품 위에 얹기"에 대한 답:** 에이전트 작업대 + 정직한 판정을 함께 가진 오픈소스 제품은 찾지 못했다 [추정]. 그래서 엔진 위에 얹는다.

## 7. Claude Design 워크플로

확인된 사실: 창업자 머신의 헤드리스 `claude -p`(Claude Code 2.1.322)에는 `/design` 명령이 없다. 따라서 **디자인은 창업자가 끼는 단계**다. omp가 대화형 PTY 세션으로 `/design`을 돌릴 수 있는지는 [확인 필요]다(D0-01b).

| 단계 | 누가 | 산출물 |

| 미리보기 실행, 탐색, 판정, 실패 리포트 | 미션·게임 규칙, 리더보드, 멀티 |
| Halo 영상 + 공유 플레이 링크 | 계정, 클라우드 저장, 호스팅된 제작 환경 |

**"완성"의 정의 [제안]:** 창업자가 빈 프로젝트에서 시작해 코드를 건드리지 않고 Halo 한 편을 끝까지 만든다. 같은 설계가 세 행성에서 실행·판정된다. 같은 프로젝트와 시드는 같은 궤적 해시를 낸다. 공유 링크를 받은 사람이 설치 없이 리플레이를 보고 프로젝트를 연다. 창업자가 헤드셋 안에서 4륜차를 조립하고 음성으로 수정 한 건을 시킨다.

정직한 한계: S1에서 "누구나"는 **보는 쪽**까지다. 제작은 로컬 설치가 필요하다. 헤드셋을 못 구하면 XR의 완성은 에뮬레이터 통과까지만 증명되고, 그 사실을 Go 자료에 적는다.

**데모 Halo:** ① 로켓 자동차 공중제비, 세 행성 비교. ② 같은 로버가 세 행성에서 경사를 오르는가. ③ (여력이 있으면) 만화 장면 한 건의 필요조건 판정.
