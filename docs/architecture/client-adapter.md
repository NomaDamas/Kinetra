# 클라이언트 어댑터 경계 (A0-04)

- 상태: 설계. 구현은 C-05(#71: C-05a #72, C-05b #73, C-05c #74)가 한다. 프레임 형식의 스키마는 C-05b가 이 문서에 잇는다.
- 근거: `docs/plan/studio-plan.md` 5.1~5.4절, `spikes/mujoco-limits/REPORT.md`의 A0-01a.
- 표기는 계획과 같다. **[추정]** 근거 없는 판단, **[확인 필요]** 채택 전 검증할 사실, **[제안]** 이 문서가 새로 내는 기준.
- 번호가 붙은 규칙(G·D·C·F·A·I·P)은 C-05c 적합성 테스트가 기준으로 삼을 문장이다. 계획이나 이슈 DoD에서 온 규칙에는 출처를 적었다. 출처가 없는 규칙, 메시지·필드 이름, 좌표 규약, 새 화면 문구는 이 문서의 [제안]이며 C-01, C-05의 스키마와 A0-05의 `engine.md`에서 확정한다.

## 1. 목적과 범위

계획 5.1절은 엔진을 하나 고르는 대신 갈아 끼울 수 있는 경계를 먼저 고정한다고 했다. 이 문서는 그 경계의 내용을 정한다. 답해야 하는 질문은 하나다. **S1에 웹 클라이언트를 쓰는 것이 최종 버전(열린 세계, 멀티와 파괴, XR, 공유 링크, 실시간 플레이)을 가두지 않는가.**

| 이 문서가 정한다 | 정하지 않는다(정하는 곳) |
|---|---|
| 코어와 클라이언트의 책임(2절) | Project 스키마(C-01 #60), Command 목록과 검증기(C-02 #65) |
| 다섯 계약의 내용과 규칙(3절) | 전송 세부, 스키마 파일, 인코딩(C-05 #71) |
| 클라이언트가 플레이 물리를 가질 때의 규칙과 화면 문구(5절) | S1 주 클라이언트, GD 트랙 착수 조건, 허용 차이(A0-05 #54 `engine.md`) |
| 최종 버전 요구와의 대조(6절) | 멀티의 네트워킹과 서버 물리(N-03 #264, N-05 #266) |

## 2. 구조와 책임

```
클라이언트(갈아 끼움)                         코어(고정, 엔진 독립)
 웹: three.js/R3F + WebXR (S1)        ─┐      Project JSON(원본), 이력
 헤드리스 참조 클라이언트 (S1, C-05c) ─┼─ 어댑터 ─ 명령 계층(Command) + 검증기
 Godot + Jolt (S2+, 조건부)           ─┘  경계     컴파일·실행·판정: MuJoCo 네이티브(권위)
 공유 플레이 페이지: 코어 없이 기록만 재생(읽기 계약만 쓴다)
 MCP 서버(G-08 #155): 화면 없는 발행자(문서 구독과 명령 발행만 쓴다)
```

| 대상 | 코어가 쥔다 | 클라이언트가 쥔다 |
|---|---|---|
| **Project** | 유일한 원본. 개정 번호, 정의 해시, 이력 | 읽기 전용 사본. 직접 고치지 않는다 |
| **명령 검증** | 스키마·불변식 검증, 적용, 역명령, 되돌리기. 발행자가 누구든 같은 검증기 | 명령을 만들어 발행한다. 거부 사유를 보여 준다 |
| 파생값(L0) | 질량, 무게중심, 정역학 경고, 값 배지, 모델 라벨 | 받은 값과 배지·라벨을 그대로 표시한다 |
| **컴파일** | Project → 엔진 모델. MJCF는 저장하지도 보내지도 않는다 | 관여하지 않는다 |
| **실행** | MuJoCo 네이티브 실행, 프레임 스트림, 실행 기록, 궤적 해시 | 스트림과 기록의 재생, 재생 위치 조작 |
| **판정** | 필요조건 스크린, 탐색, 몬테카를로, 민감도, 판정 카드의 내용 | 요청과 표시만 한다. 만들거나 고치지 않는다 |
| 에셋 | 원장, 출처, 내용 해시, 시각 메시와 물리 기술의 제공 | 내려받기, 캐시, 그리기 |
| **렌더** | 없다 | 장면, 카메라, 조명, 고스트, 배지와 문구의 표시, 시각 전용 효과(파도 등) |
| **입력** | 없다. 받는 것은 Command와 조종 입력뿐이다 | 장치 읽기, 선택·호버·드래그, 장치 → 조종 채널 바인딩, XR 세션 |
| 플레이 물리(선택) | 없다. 그 결과를 받지 않는다 | 자체 물리로 그릴 수 있다. 5절의 규칙을 따른다 |

굵은 행이 계획 5.1절과 이슈 DoD가 이름 붙인 것이다. 한 줄 시험: **클라이언트를 지워도 Project, 이력, 실행 기록, 판정은 남는다. 코어를 지우면 클라이언트는 이미 기록된 것을 재생하는 일만 할 수 있다.**

에이전트는 클라이언트가 아니다. LLM 도구 호출 → Command → 검증기의 경로로 명령 계층에 붙는다(계획 5.3절). 에이전트를 부르는 경로는 다섯 계약 밖이고 G 에픽이 정한다. 경계가 고정하는 것은 변경안이 3.2의 명령 발행을 거친다는 점이다.

## 3. 다섯 계약

공통 규칙:

- **G1 전송 중립.** 계약은 메시지의 내용이다. S1의 전송은 WebSocket(C-05a)이고 공유 링크는 정적 파일이다. 같은 내용이 두 전송에서 같은 뜻이어야 한다.
- **G2 엔진·렌더러 중립.** 경계를 넘는 어떤 것에도 MuJoCo 용어(`qpos`, `geom`, `eq`, MJCF 등)나 렌더러 용어(three.js 객체, Godot 노드)가 없다. 스키마는 언어 중립(JSON Schema)으로 쓴다 [제안].
- **G3 식별자.** 부품, 강체, 결합, 조건, 에셋은 Project의 안정 ID로 가리킨다. 엔진 내부 번호를 쓰지 않는다.
- **G4 단위와 좌표.** Project와 같은 규약 하나만 쓴다. SI(m, kg, s, rad), 오른손 좌표계, +Z가 위, 쿼터니언은 성분 이름을 스키마에 적는다. **확정(C-01a, `docs/architecture/project-model.md`): Project JSON에서 쿼터니언은 `{x, y, z, w}`(`w`가 스칼라, 단위 길이) 객체이고 배열로 쓰지 않는다. 실행 스트림 프레임은 같은 성분 순서와 뜻(x, y, z, w; w 스칼라)만 따르고 인코딩은 C-05b가 정한다. 단위 어휘는 닫혀 있다.** 자기 렌더러의 좌표로 바꾸는 일은 클라이언트가 한다.
- **G5 버전.** 첫 메시지에서 프로토콜 버전을 주고받는다. 모르는 선택 필드는 무시하고, 필수 필드가 늘면 버전을 올린다. 3절 각 항의 "열어 둔 것"은 이 규칙으로 더한다.
- **G6 값에는 출처.** 수치가 경계를 넘을 때 값 배지(`시뮬` `인용` `기본값` `사용자 선언` `추정`)와 단위가 함께 간다.

### 3.1 문서 구독

| 메시지 [제안] | 방향 | 내용 |
|---|---|---|
| `subscribe` | 클라이언트 → 코어 | 프로젝트 ID. 재접속이면 마지막으로 받은 개정 번호 |
| `snapshot` | 코어 → 클라이언트 | Project JSON 전체, 개정 번호, 정의 해시, 파생값, 판정 상태(없음, 유효, 무효) |
| `applied` | 코어 → 클라이언트 | 새 개정 번호, 적용된 명령 묶음과 발행자, 그 결과로 바뀐 문서 부분·파생값·판정 상태 |

- **D1** Project JSON이 원본이고 코어에만 있다. 클라이언트의 사본은 `snapshot`과 `applied`로만 바뀐다.
- **D2** 개정 번호는 코어가 매긴다. 같은 `snapshot`에 같은 순서의 `applied`를 받은 클라이언트들은 같은 문서를 갖는다(C-05a의 두 클라이언트 동기화 테스트).
- **D3** `applied`는 명령과 함께 그 결과를 담는다. 클라이언트는 명령 적용기를 다시 구현하지 않는다 [제안]. 이유: 적용기가 클라이언트마다 있으면 서로 어긋난다.
- **D4** 파생값, 값 배지, 모델 라벨(`근사: …` 등)은 코어가 계산해 보낸다. 클라이언트가 따로 계산한 수치를 대신 보여 주지 않는다.
- **D5** 문서가 바뀌어 이전 판정이 무효가 되면 그 사실이 같은 `applied`에 실린다(계획 4.6절).
- **D6** 재접속하면 마지막 개정 뒤의 `applied`를 이어 받는다. 코어가 이어 줄 수 없으면 새 `snapshot`을 준다.
- **D7** 선택, 호버, 카메라, 고스트는 문서가 아니다. 구독으로 오가지 않는다.

S1 범위: 프로젝트 하나, 문서 전체 스냅샷. 발행자는 사용자 한 명, 에이전트, MCP다.
열어 둔 것: `subscribe`에 범위(영역, 하위 조립체)를 더하는 것(열린 세계). 발행자가 모든 `applied`에 있으므로 여러 사용자를 구분할 수 있다(멀티).

### 3.2 명령 발행

| 메시지 [제안] | 방향 | 내용 |
|---|---|---|
| `publish` | 클라이언트 → 코어 | 발행자가 붙인 명령 ID, 기준 개정 번호, 명령 묶음, 발행자 |
| `accepted` | 코어 → 클라이언트 | 명령 ID, 새 개정 번호 |
| `rejected` | 코어 → 클라이언트 | 명령 ID, 사유 목록(코드, 읽을 수 있는 문장, 관련 대상 ID) |
| `request` | 클라이언트 → 코어 | 되돌리기·다시 하기, 컴파일·실행, 정지, 판정 요청 |

- **C1** Project를 바꾸는 길은 `publish`와 되돌리기 요청뿐이다. 화면, XR, 음성, 에이전트, MCP가 모두 같은 검증기(C-02c #68)를 거친다.
- **C2** 묶음은 전부 적용되거나 전부 거부된다. 에이전트 변경안의 부분 수락은 고른 명령만 묶어 발행하는 것이다.
- **C3** 거부에는 항상 사유가 온다(C-05a). 클라이언트는 결과를 미리 그려도 되지만(고스트) 거부되면 버린다.
- **C4** 행성 상수, 물성 DB, 판정 결과를 바꾸는 명령은 누가 보내도 거부된다(C-02c). 판정 결과는 코어 → 클라이언트로만 흐른다.
- **C5** 순서는 코어가 정한다. 기준 개정이 낡은 명령은 현재 문서에 대해 다시 검증하고 통과하지 못하면 거부한다. S1에는 병합 알고리즘이 없다.
- **C6** 같은 명령 ID를 다시 보내도 한 번만 적용된다(재접속 뒤의 재전송).
- **C7** 실행·판정 요청은 Project를 바꾸지 않는다. 결과로 실행 스트림(3.3)이나 판정 카드의 내용(J 에픽의 스키마)이 온다.

S1 범위: 위 전부. 열어 둔 것: 여러 사용자의 동시 편집 충돌 정책(N-04 #265). 코어가 정하는 전순서와 발행자 ID는 그 바탕이 된다.

### 3.3 실행 스트림 프레임

| 메시지 [제안] | 방향 | 내용 |
|---|---|---|
| `run_started` | 코어 → 클라이언트 | 실행 ID, 문서 개정 번호와 정의 해시, 행성, 시드, 시간 간격, 프레임 간격, 강체 목록(강체 ID ↔ 부품 ID), 실행 종류(미리보기 1회, 판정 표본), 모델 라벨 |
| `frame` | 코어 → 클라이언트 | 틱(정수), 시뮬 시각 [s], 강체별 자세(위치 [m], 방향 쿼터니언), 이벤트 목록 |
| 이벤트 | `frame` 안 | 종류(접촉, 파단, 조건 충족), 틱, 관련 ID(강체, 결합, 조건), 종류별 수치와 단위 |
| `control` | 클라이언트 → 코어 | 실행 ID, 조종 채널 ID, 값 |
| `run_ended` | 코어 → 클라이언트 | 종료 사유, 마지막 틱, 궤적 해시 |

- **F1** 프레임과 이벤트에 MuJoCo 용어가 없다(C-05b의 DoD).
- **F2** 시간은 틱과 시뮬 시각이다. 벽시계 시각에 뜻을 두지 않는다. 코어가 실시간보다 느리든 빠르든 형식은 같다(4절).
- **F3** 라이브 스트림과 기록은 같은 형식이다. 리플레이, Halo 캡처(H-01 #188), 공유 번들(H-03a #197)이 같은 프레임을 재생한다. 공유 페이지는 다시 시뮬하지 않는다(계획 5.3절 결정론 행).
- **F4** 클라이언트는 궤적을 바꾸지 않는다(V4). 그리기용 보간은 받은 두 프레임 사이에서만 한다. 받은 프레임 너머를 예측해 그린 자세는 코어의 궤적이 아니므로 5절을 따른다. 재생 배속이 1이 아니면 화면에 표시한다 [제안].
- **F5** 조종 입력은 코어가 적용한 틱과 함께 실행 기록에 남기고, 리플레이는 그 기록을 재생한다(X-02c #130).
- **F6** 실행 종류가 미리보기이면 클라이언트는 "1회 실행. 판정이 아닙니다"를 표시한다(계획 4.5절 L1). 프레임 스트림에서 판정이 만들어지지 않는다.
- **F7** 궤적 해시는 코어가 계산한다(X-02d #131). 클라이언트가 계산한 해시는 증거가 아니다.
- **F8** 프레임이 강체를 가리키는 방법은 실행 도중 강체 목록이 바뀌어도 모호하지 않아야 한다. S1에서는 목록이 고정이다. S1의 파단은 결합이 풀리는 것이고 강체 수는 그대로다(X-04b #138).

S1 범위: 매 프레임에 모든 강체. 조종은 키보드(X-02c).
열어 둔 것: 강체가 생기고 없어지는 실행(파편), 관심 영역만 담는 부분 프레임, 이진 인코딩과 프레임률. 뒤의 둘은 C-05b에서 정한다. 포즈 스트림 대역폭과 입력 지연의 측정은 나왔다(A0-02a #47, `spikes/web-client/REPORT.md`): 전 강체 float32 7개(28 B)를 60 Hz로 보내면 200 / 1,000 / 5,000개가 2.70 / 13.45 / 67.21 Mbit/s이고 gzip·brotli는 6 %만 줄였다. 인코딩 대안(양자화, 변화분, 관심 영역)은 재지 않았다 [확인 필요].

### 3.4 에셋 로딩

| 항목 [제안] | 내용 |
|---|---|
| 에셋 참조(문서 안) | 에셋 ID, 내용 해시, 종류 |
| 에셋 본문 | 해시로 요청해 받는다. 시각 메시는 glTF 2.0(glb) |
| 에셋 메타 | 출처, 라이선스, 표기 문구, 가져온 에셋인지와 선언값인지 |

- **A1** 시각 메시와 물리 모델은 따로다. glTF는 그리기에만 쓴다. 물리에 쓰는 것(충돌 프록시의 형상, 질량, 무게중심, 관성, 결합, 한계, 파단 임계)은 Project와 부품 정의의 엔진 중립 데이터로 온다. MJCF 조각으로 오지 않는다.
- **A2** 에셋은 내용 해시로 가리키므로 바뀌지 않는다. 캐시, 정적 호스팅, 공유 번들에서 코어 없이 열린다.
- **A3** 출처와 라이선스 메타가 함께 온다(V5, `assets/LEDGER.csv`). 클라이언트는 가져온 에셋과 선언값의 배지를 표시한다.
- **A4** 에셋을 프로젝트에 넣는 일(glb 가져오기)은 명령 발행으로 한다. 클라이언트는 Project가 참조하지 않는 에셋을 부품으로 그리지 않는다.
- **A5** 생성 3D는 시각 스킨이다. 물리 형상이 되지 않는다(계획 4.4절).
- **A6** 렌더러 전용 형식(three.js JSON, Godot 장면 파일)은 경계를 넘지 않는다.

S1 범위: 부품마다 glb 하나. 열어 둔 것: 참조가 ID와 해시이므로 LOD 변형과 영역 단위 스트리밍을 더할 수 있다(열린 세계).

### 3.5 입력 → Command

| 입력 | 클라이언트 안에서 끝난다 | 경계를 넘는다 |
|---|---|---|
| 마우스·키보드 | 호버, 선택, 드래그 중의 위치, 고스트 | 놓는 순간의 Command(이동, 결합 등) |
| XR 손·컨트롤러 | 손의 자세, 잡고 있는 동안의 위치, 스냅 후보 고스트, 작업대 스케일 | 놓는 순간의 같은 Command |
| 텍스트 | 입력창 | 에이전트가 낸 변경안 중 수락한 명령의 `publish` |
| 음성 | 받아쓰기, 인식문 확인, 삭제류의 확인 단계 | 확인된 문장. 그 뒤는 텍스트와 같다 |
| 실행 중 조종 | 키 → 조종 채널 바인딩 | `control`(3.3) |

- **I1** 입력 수단마다 다른 Command는 없다. 같은 동작은 같은 Command다(XR-02 #208의 "데스크톱과 같은 스냅 규칙").
- **I2** Command는 문서의 말로 쓴다: 부품 ID, 스냅 포인트 ID, 파라미터 이름과 SI 값. 화면 좌표, 레이, 손 관절의 자세는 경계를 넘지 않는다.
- **I3** 고스트를 위한 스냅 후보는 클라이언트가 문서의 스냅 포인트로 계산한다. 붙는지는 코어 검증기가 정한다. 둘이 다르면 코어가 옳다.
- **I4** 드래그 중의 연속 입력은 Command가 아니다. 이력의 한 칸은 사용자가 확정한 동작 하나다.
- **I5** 실행 중 조종 입력은 편집 Command가 아니다. Project를 바꾸지 않고 이력에 들어가지 않으며 실행 기록에 남는다(F5). 조종 채널은 Project의 액추에이터·제어 정의에서 오고, 어느 키가 어느 채널인지는 클라이언트가 정한다.

S1 범위: 계획 4.3절의 네 입력 모드와 키보드 조종. 헤드셋 안 조종은 S1 밖이다.
열어 둔 것: OpenXR 입력(GD-04 #252)과 웹캠 손 입력은 같은 Command로 온다. 다른 사용자의 손과 커서(프레즌스)는 문서도 Command도 아닌 별도의 휘발성 채널로 더한다(N-04).

## 4. 실시간 질문: 잰 것과 모르는 것

A0-01a(#43)가 잰 MuJoCo 네이티브의 실시간 배속(1.0 = 실시간)이다. 출처는 `spikes/mujoco-limits/REPORT.md`이고 조건은 Apple M2 Pro 10코어, MuJoCo 4.0.0, `timestep=0.002`, Euler, 단일 스레드, 시드 0, 측정 중 load average 50~195다.

| 장면 | 배속 | 프로세스 CPU 시간 기준 배속 | 값 배지 |
|---|---|---|---|
| 박스 200개 | 0.02~0.03 | 약 0.2 | `추정`(부하 아래 측정) |
| 박스 1,000개 | 약 0.007 | 약 0.045 | `추정` |
| 박스 5,000개 | 0.002~0.003 | 약 0.016 | `추정` |
| 결합 해제 100건(박스 100개 단독) | 0.5~0.6 | 2.7~3.0 | `추정` |
| 같은 시드 반복의 궤적 해시 | 측정한 모든 장면에서 일치 | — | `시뮬` |

- 계획 5.2절의 문턱 [제안] "S1은 200개 실시간"에 닿지 못했다. 다만 보고서가 스스로 밝히듯 이 값은 다른 작업이 머신을 점유한 상태의 비관적 값이고, 1,000개와 5,000개는 낙하 초기 0.24~0.5초만 쟀다. 결합 해제 100건을 박스 1,000개와 합친 장면은 30~31건에서 상한에 걸려 완주하지 못했다. 한가한 머신의 재측정은 #332(A0-01d)이고 아직 열려 있다.
- 그래서 **코어의 실행 스트림만으로 실시간 플레이가 되는지는 지금 모른다.** 이 문서는 된다고도 안 된다고도 쓰지 않는다.
- 함께 모르는 것: 코어가 실제로 낼 수 있는 프레임 속도(위), 브라우저 WASM(A0-01b #44), 재컴파일 시간(A0-01c #45), Jolt의 같은 항목(A0-03 #50). 조종 입력 → 화면 지연과 포즈 스트림 대역폭은 A0-02a(#47, `spikes/web-client/REPORT.md`)가 코어를 합성 생성기로 바꾼 루프백에서 쟀다: GPU 경로 중앙값 25~29 ms(200 / 1,000 / 5,000개). 키 이벤트에서 캔버스 픽셀까지만이고 물리 스텝, 실제 네트워크, 디스플레이 출력은 빠졌다. 문턱 [제안] "로컬 100 ms 이하"의 전체 대조는 코어 시간이 들어와야 한다.

경계는 이 답을 기다리지 않도록 두 구성을 같은 계약으로 받는다.

| 구성 | 화면의 물리 | 판정 | 쓰는 곳 |
|---|---|---|---|
| A. 코어 재생 | 코어의 프레임을 그대로 그린다 | 코어 | S1 권고(계획 5.2절). 플레이와 판정이 갈리지 않는다 |
| B. 클라이언트 플레이 물리 | 클라이언트의 물리(Jolt, 조건부 WASM) | 코어 | 코어 스트림이 실시간에 못 미칠 때의 후보. 5절의 규칙이 붙는다 |

구성 A에서 코어가 실시간보다 느리면 클라이언트는 받아 둔 뒤 재생하거나 느리게 보여 준다(F2, F4). 어느 구성을 언제 쓰는지는 `engine.md`(A0-05 #54)가 #332와 A0-02, A0-03의 수치로 정한다. 이 문서는 그 선택을 미리 하지 않는다.

## 5. 클라이언트가 플레이 물리를 가질 때의 규칙

플레이 물리는 코어의 MuJoCo 네이티브 실행이 아닌 물리로 화면을 그리는 모든 경우다: GD 트랙의 Jolt, 브라우저 WASM 미리보기(X-05 #140, 조건부), 받은 프레임 너머의 예측(F4). 실시간 대결은 서버 물리 위에서 하더라도 "플레이 물리"로 표시한다(계획 15.3절).

- **P1 판정은 항상 코어가 낸다.** 판정(L2)과 그 수치(p_success, CI, 가정표, 민감도)는 코어의 MuJoCo 네이티브 실행에서만 나온다. 클라이언트의 궤적을 코어로 보내는 메시지는 없고, 플레이 물리의 결과는 판정 엔진의 입력이 되지 않는다.
- **P2 같은 원본.** 플레이 물리의 세계는 같은 개정의 Project와 코어가 준 물리 기술(A1), 행성 데이터로만 만든다. 클라이언트에 상수의 사본이나 리터럴을 두지 않는다.
- **P3 항상 표시.** 플레이 물리로 그리는 동안 아래 표의 문구가 화면에 있고 접거나 숨길 수 없다. 그 화면은 판정(L2)의 배지와 문구를 달지 않는다.
- **P4 조건 충족은 판정이 아니다.** 성공 조건이 플레이 물리에서 충족돼도 판정 카드는 생기지 않는다. 판정은 코어에 요청한다(C7).
- **P5 기록과 Halo.** 판정 자막(p_success, CI)이 붙는 영상과 공유 링크의 궤적은 코어의 실행 기록이다. 플레이 물리 화면을 담은 영상에는 P3의 표시가 남는다.
- **P6 일치는 수치로만 말한다.** 플레이 물리와 판정 물리의 차이는 기준 장면의 측정(A0-03b #52, GD-02 #250)으로만 말한다. 수치가 없으면 "판정과 같다", "비슷하다"고 쓰지 않는다. 허용 차이는 `engine.md` 5절이 정한다.
- **P7 플레이 상태는 문서가 아니다.** 플레이 물리 안에서 부서지고 움직인 것은 Project를 바꾸지 않는다. 남기려면 Command로 발행하고, 그 명령은 다른 편집처럼 이전 판정을 무효로 만든다(D5).

| 화면에 보이는 것 | 물리의 출처 | 표시 문구 | 판정 카드 |
|---|---|---|---|
| 코어의 1회 실행(라이브, 리플레이) | 코어 | "1회 실행. 판정이 아닙니다" (계획 4.5절) | 없다 |
| 판정에 쓰인 표본의 재생 | 코어 | L2 문구와 "표본 중 하나"라는 표시 (계획 4.5, 4.6절) | 코어가 낸 카드 |
| 브라우저 WASM으로 다시 실행 | 클라이언트 | "미리보기. 판정이 아닙니다" [제안] (계획 5.3절의 "미리보기") | 만들지 않는다 |
| 플레이 물리(Jolt 등) | 클라이언트 또는 대결 서버 | "플레이 물리. 판정이 아닙니다" [제안] (계획 5.1절의 "플레이 물리") | 만들지 않는다 |
| 플레이 물리에서 조건 충족 | 위와 같다 | "플레이 물리에서 조건 충족. 판정이 아닙니다" [제안] | 만들지 않는다 |

플레이 물리 화면에 쓰지 않는 문구: "현실과 동일"(계획 2절의 금지), 성공·실패의 단정, p_success·CI·`FEASIBLE_FOUND` 같은 판정의 말. 플레이 물리 화면 옆에 이미 낸 판정 카드를 함께 둘 때는 그 판정이 지금 보이는 궤적의 것이 아니라고 표시한다 [제안]. [제안] 문구의 최종본은 `engine.md` 5절과 디자인 승인본에서 정한다.
