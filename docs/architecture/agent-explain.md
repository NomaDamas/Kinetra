# 에이전트 실패 설명 (G-05)

- 상태: 구현됨. 코드는 `packages/engine/src/kinetra_engine/agent/explain.py`, 테스트는 `packages/engine/tests/test_explain.py`(`uv run pytest packages/engine -q -k explain`).
- 근거: `docs/plan/studio-plan.md` 4.4절("롤아웃 수치만 인용한 실패 설명", G-05 "응답 속 수치가 데이터에 있는지 검사"), 이슈 #152. 데이터는 G-02b 조회 도구([`agent-query-tools.md`](agent-query-tools.md))가 내는 그대로다: 실행 요약(X-02a 실행 스트림, X-02d 궤적 증거, X-04b 파단 이벤트)과 검사(X-03a 정역학, 질량). 설명의 라벨과 판정 거르개는 G-03a([`agent-proposal.md`](agent-proposal.md))의 `Explanation`이다. 모델 호출은 G-01 게이트웨이다.
- 범위 밖: 설계 자동 수정(설명은 고칠 것을 제안하지 않는다). 화면(G-07 에이전트 바), MCP 노출과 실행 기록 연결(#558). 실패 원인 분류(J-04d): 들어오면 그 결과를 증거에 더한다.

## 쓰는 법

```python
from kinetra_engine.agent import Explainer, QueryTools
tools = QueryTools()
tools.record(started, frames, ended)                         # 끝난 실행 (G-02b)
result = Explainer(gateway).explain("tower", project, tools, "왜 무너졌어?", run_id="run-1")
result.status       # "explained" | "discarded" | "no_run" | "budget_exceeded" | "gateway_error"
result.to_json()    # 화면에 보낼 것: 라벨 붙은 설명과 수치마다의 출처, 또는 왜 없는지
```

## 규칙

- **데이터는 코어가 계산한 것이다.** `evidence_of(tools, project, run_id)`가 조회 도구로 `rollout_summary`(실행 하나의 요약: 끝 사유, 틱, 강체마다의 위치·최저·최고·기울기, 파단·조건 충족 이벤트, 궤적 해시와 플랫폼 태그), `statics_check`, `mass_properties`를 읽어 `{"rollout_summary": …, "statics_check": …, "mass_properties": …}`를 만든다. 모델은 이 JSON과 사용자의 질문만 받는다. 기록된 실행이 없으면 설명할 것이 없으므로 모델에게 묻지 않는다(`no_run`, 조회 도구의 `unknown_id` 사유). 코어가 검사를 못 내는 설계(컴파일되지 않음)는 그 검사를 빼고 `unavailable`에 도구 이름과 사유 코드만 적는다. 수치를 지어 채우지 않는다.
- **응답 속 모든 수치가 데이터에 있어야 하고, 하나라도 없으면 응답을 통째로 버린다.** `check_numbers(text, evidence)`가 답의 숫자를 하나씩 읽어(`NUMBER`) 그 숫자로 반올림되는 데이터 값을 찾는다:
  - 데이터 값은 증거의 JSON 숫자 전부와 문자열 속 숫자(해시, 문장)다. 참·거짓은 숫자가 아니다.
  - 답에 쓴 소수 자릿수로 데이터 값을 반올림해 같으면 인용이다(`0.12`는 0.1234의, `6`은 5.832의 인용이다. 경계는 양쪽 다 받는다). 지수 표기는 지수만큼 자릿수를 센다.
  - 답에 쓴 빼기 부호는 데이터의 부호여야 한다. 부호 없는 숫자는 음수 데이터의 크기일 수 있다("0.08 m 모자람"은 여유 -0.08 m의 인용이다).
  - 단위를 바꾼 숫자는 인용이 아니다(0.08 m를 8 cm로 쓰면 버린다). 질문 속 숫자도 데이터가 아니다.
  - ASCII 식별자에 이어진 숫자는 식별자의 일부다(`plate-1`, `run-2`, `X-02d`, `al6061`, `sha256`). 한글 뒤에 붙은 숫자는 숫자다(`틱25`).
  
  없는 숫자가 하나라도 있으면 상태는 `discarded`, 화면에는 `DISCARDED_NOTICE`("에이전트 설명에 실행·검사 데이터에 없는 수치가 있어 버렸습니다")와 버린 숫자의 개수만 간다. 근거 있는 문장만 골라 보이지 않는다(답 전체가 지어낸 원인을 담았을 수 있다). 답 원문(`reply`)과 없는 숫자(`ungrounded`)는 평가용으로 결과 객체에만 남는다.
- **설명은 판정이 아니다(V1).** 검사를 통과한 답은 G-03a의 `Explanation.of`가 된다: 내용과 상관없이 `{"by": "agent", "is_verdict": false, "label": EXPLANATION_LABEL, …}`이 붙고, 판정처럼 읽히는 문장은 보이기 전에 빠진다(`notice` = `VERDICT_NOTICE`). 수치 검사는 거르개보다 먼저 답 전체에 건다: 빠질 문장 속 지어낸 숫자도 답을 버리게 한다. 실행 요약에는 언제나 `ROLLOUT_NOTICE`("1회 실행. 판정이 아닙니다")가 있다.
- **수치마다 출처가 화면에 간다.** `to_json()`의 `citations`는 화면에 남은 설명의 숫자마다 쓴 그대로(`text`), 증거 안의 경로(`path`, 예: `rollout_summary.breaks[0].load.value`), 그 데이터 값(`value`)이다. 같은 숫자로 반올림되는 값이 여럿이면 가장 가까운 것, 같으면 문서 순서로 먼저인 것이다. `run_id`와 `sources`(쓴 조회 도구)도 함께 간다.
- **설명 하나에 게이트웨이 호출 하나다.** 프로젝트 예산에 잡힌다(G-01). `BudgetExceeded`는 `budget_exceeded`, 다른 게이트웨이 오류는 `gateway_error`(게이트웨이가 이미 가린 문장)다. 장부 쓰기 실패(`LedgerWriteError`)에 답이 실려 있으면 돈이 이미 나갔으므로 그 답을 검사한다(G-03a와 같다). 버린 답을 다시 묻지 않는다.
- **모델이 보는 것.** 시스템 메시지는 검사가 강제하는 것을 말할 뿐이다: 수치는 데이터의 것을 데이터의 단위로(그대로나 반올림), 단위 변환·셈·추정 금지, 데이터가 원인을 보이지 않으면 그렇다고 말하기, 판정·확률·성공/통과/실패 단정 금지, 편집 제안 금지, id는 그대로. 지키는 것은 `check_numbers`와 `Explanation`이다.

## 한계 (숨기지 않는다)

- 검사는 숫자 대조다. 데이터 어딘가에 우연히 같은 값(반올림 범위 안)이 있으면 지어낸 숫자도 지나간다. 자릿수가 적을수록 범위가 넓다: 정수는 ±0.5 안의 아무 값과 맞고, 실행 요약에는 틱, 프레임 수, 플랫폼 태그의 판 번호와 솔버 설정 같은 작은 정수가 많다. 숫자가 맞아도 그 숫자를 다른 뜻으로 쓴 문장(하중을 임계라고 부르기)은 잡지 못한다. `citations`의 경로가 화면에서 그것을 확인하게 한다.
- 수 낱말("두 번", "절반")과 쉼표 묶음(`1,000`은 1과 0으로 읽힌다)은 숫자로 따로 다루지 않는다. 낱말은 검사를 지나가고, 쉼표 묶음은 대개 버려진다.
- 16진 해시 속 숫자는 같은 규칙으로 읽는다(`sha256:7e83…`의 `7e83`은 지수 표기 수로 읽힌다). 해시를 그대로 옮긴 답은 같은 수가 나오므로 지나간다.
- 반올림 경계의 허용 오차(상대 1e-9, 절대 1e-12)는 부동소수점 표현 오차를 받기 위한 설계 선택이다(출처 없음).
- G-03a 거르개는 성공·통과·실패 낱말이 숫자와 같은 문장에 있으면 문장을 뺀다. 실패 설명이 "실패"와 숫자를 한 문장에 쓰면 빠지므로 프롬프트가 그 낱말을 피하게 한다. 판정을 거절하는 문장이 빠지는 문제는 #542다.
- 버린 답을 사유와 함께 다시 묻지 않는다(호출 하나). 호출자가 다시 부를 수 있다.
